## 五、踩到的坑（4 个）

### 5.1 FFT 幅度标度少了整整一个 N（**由自检抓到，非肉眼发现**）

首轮自检报：

```
[FAIL] VizAnalyzer：FFT 峰值 / RMS / 相关度 / 60Hz 限频
首帧算=是 紧接第二次=否；峰值 bin=93（期望 93）；峰柱=29 高 0.021；
RMS=0.424（理论 0.707，首帧平滑后≈0.42）；相关 同相 0.83 / 反相 0.556
```

**读数**：峰值 bin 精确命中、RMS 量级对、相关度方向对、限频生效 —— **只有柱高错**。

**反解**：首帧 `cur=0`、`attack=0.55` → `target = 0.021/0.55 ≈ 0.038` → 反推 `db ≈ −72.3 dB`。
满幅正弦理应是 **0 dBFS**，差 **72 dB** = 幅度差 `10^(72/20) ≈ 4000` ≈ **4096 = FFT 点数**。

**根因**：**NAudio 3.0 的 `FastFourierTransform.FFT` 输出已含 `1/N` 归一化**。XML 文档不写这一点，
而 2.x 时代的通行说法是「未归一化正变换：满幅正弦模 ≈ N/2」，照那条推就会**多除一个 N**。

```csharp
// 旧（错）：按 2.x 的 lore 推
float scale = 1f / (n * 0.5f * HannCoherentGain);   // = 1/1024
// 新（对）：实测模 = A·(N/2)·增益·(1/N) = A·增益/2
float scale = 2f / HannCoherentGain;                // = 4
```

**验证**：实测峰值模 = `10^(−72.33/20) ÷ (1/1024)` = **0.2478**；1/N 归一化理论值
`A·增益/2 = 0.25` 再乘 Hann 非整 bin 的扇贝损失（≈0.99）得 **0.2475** —— 差 **0.1%**，结论可钉死。
修后自检报 **峰柱=29 高 0.55**，与预测的 0.55 逐位吻合。

**影响面**：M1 只接了示波器（不吃 FFT），画面上**完全看不出来**；M2 一挂 A 区频谱条就会「柱全趴」，
而这种表现更像渲染器写坏了，定位反而更绕。→ **教训：涉 FFT/DSP 的绝对标度，一律用「满幅正弦 → 0dBFS」反解，别照搬他版本 lore。**

### 5.2 NAudio 3.0 的破坏性改动（3 处，均与可视化逻辑无关）

| 项 | 2.x 写法 | 3.0 写法 |
| --- | --- | --- |
| 输出设备 | `WaveOutEvent` | **`WaveOut`**（前者已标 `[Obsolete]`，语义相同） |
| 缓冲延迟 | `DesiredLatency = 100` | **`BufferMilliseconds = 50` × `NumberOfBuffers = 2`**（3.0 去掉了 `DesiredLatency`，这两个属性就是它拆出来的；2×50ms = 旧写法等价） |
| `IWaveProvider` | `Read(byte[], int, int)` | **`Read(Span<byte>)`**（三参数重载已不在接口上 → 只写数组版直接 CS0535） |
| `ISampleProvider` | `Read(float[], int, int)` | **`Read(Span<float>)`**（同样只剩 Span 版；返回语义不变） |
| 窗函数 | `HannWindow` 返回 **double** | 返回类型没变，但 **XML 文档不显示返回类型** → 写 `float[]` 时容易漏，要显式 `(float)` 收敛 |

**核对方式（值得复用）**：读 NuGet 包自带的 XML 文档 ——
`C:\Users\Mika\.nuget\packages\<包>\<版本>\lib\<tfm>\<包>.xml`，是全部 public 成员的权威签名。
**但它不给返回类型、也不给数值语义**（§5.1 的坑正出在后者）。

> `TapProvider.Read` 的返回策略：**永远填满并返回整长**，解码到头时尾部填静音。
> 返回 0 会让 `WaveOut` 立即判定流结束并触发 `PlaybackStopped`；我们要的是「窗口继续开着、画面自行衰减」。
> 结束状态由 `IsPlaying`（读 `_ended`）对外表达，不靠返回值。

### 5.3 FFT 输入「补零」与 Hann 窗周期错配（自查发现，未进 build）

最初把「FFT 点数」与「取多少真实样本」当成同一件事：只取 2048 个真实样本再补零到 4096。
那样信号落在索引 2048–4095，按 4096 周期算出来的 Hann 窗在那段只走完后半截 ——
**是个从 1 直落 0 的不对称斜坡，而不是 Hann 窗**，旁瓣明显变差、柱高整体偏低。

**修法（对齐参照页 `anMix` 4096 / `anL·anR` 2048）**：

- `TimeFrames = FftSize = 4096` —— 一次取满喂 FFT，**不补零**；
- 新增 `WaveFrames = 2048` + `WaveL` / `WaveR`，B/C/D 用后者；
- 一次取数、拷贝出两种视图，比让 feed 读两遍干净。

### 5.4 `VizPanel.Style` 隐藏了 `FrameworkElement.Style`（CS0108）

面板最初把观感资源暴露成 `public VizStyle Style` —— 撞基类，且 XAML 里任何 `Style="…"` 都会往它写、
类型对不上会在运行时炸。改名为 **`Skin`**。
→ **给 `FrameworkElement` 派生类加公开属性的规范动作：先查基类有没有同名成员。**

## 六、里程碑纪律：音频线程零分配无锁（**已确认成立**）

方案 §九的硬性要求：`VizTap.Read` 是音频线程上唯一的新代码，任何一处 `new` 都会让 GC 在播放时持续抖动。

| 检查点 | 结论 |
| --- | --- |
| 音频线程上的代码 | 只有 `TapProvider.Read(Span<byte>)` 一处 |
| 缓冲 | `_scratch`（`float[32768×2]`）、`_ringL`/`_ringR`（`float[65536]`）均**构造期分配** |
| `Read` 内的分配 | **零** —— 只做 `_decoder.Read(_scratch, …)` → `WriteRing` → float→int16 折写 |
| 同步 | 单写单读：写指针 `_written` 单调递增，`Volatile.Read/Write`；**不加锁** |
| 环长度取模 | `RingFrames = 1 << 16`（2 的幂）+ 位与，不做除法 |
| 写指针推进 | `WriteRing` 末尾**一次性**推进 → 读到旧指针的 UI 线程至多看到「少一段」，读不到半截脏数据 |
| `VizAnalyzer.Update` | 所有缓冲构造期分配、原地复用；活在 **UI 线程**（每秒 60 次），不在音频线程 |
| 渲染侧 | `OscilloscopeRenderer` 复用 `List<Point> _pts`；`Pen` / `FormattedText` 按 DPI 缓存 |

## 七、追加：调试源支持 Opus（同日，用户选「A + B」）

**起因**：`--viz "...\viz-demo\th06nc_16.ogg"` 报 `打不开调试声源：Could not find Vorbis data to decode.`

**诊断（不是 bug，是编码不匹配）**。新建只读探针 `.workbuddy/tools/ogg_probe.py`（打印 Ogg 页结构与编码标识）实探：

| 文件 | 真实编码 | 证据（page 0 payload） |
| --- | --- | --- |
| `release/tf/th175/dat/data.cga/data/bgm/op.ogg` | **Vorbis** | `\x01vorbis` → ch=2 **sr=44100** |
| `.workbuddy/viz-demo/th06nc_16.ogg` | **Ogg Opus** | `OpusHead` → ch=2 preskip=0 **input_sr=48000** |

后者是 demo 期从新典原生 `.opus` 复制改名而来的 scratch 产物；`VorbisPizza` 只认 `\x01vorbis`，
扫不到就抛 NVorbis 那句黑话。**编码不匹配，与路径、容器完整性无关。**

顺带查清（对 M6 有用）：

- 新典**原生** `.opus` 是**自定义容器**（头 8 字节 `01 00 00 80 18 00 00 00`，非 `OggS`，全库无 `OpusHead`）：
  40 字节头 + N×488 记录，每记录 `[8:488]` 是 480B 裸 Opus 包（960 帧 @48kHz）。
- 项目**已有**两条解码源：`src/Audio/Tf/OggMemorySource.cs`（Vorbis）、`src/Audio/Nc/OpusMemorySource.cs`（Concentus）。
  **Concentus 2.2.2 早就是 csproj 依赖**（BSD-3-Clause，可入 GPL-3.0）。
- **唯一缺口 = 标准 Ogg Opus 容器解析**：Concentus 2.x 已移除 `Concentus.Oggfile` / `OpusOggReadStream`。

**决策**：**A（明确拒绝）＋ B（接上原生 `.opus`）**；**C（自写 Ogg 页解析支持标准 Ogg Opus）不做**。

**实现**（全在 `src/Viz/VizDebugFeed.cs`）：

1. `CreateDecoder` 路由三路：`.wav` / `.ogg` → `CreateOggDecoder` / `.opus` → `CreateOpusDecoder`。
2. **`.ogg` 不再只看扩展名** —— 先 `SniffOggCodec` 解第一个 Ogg 页的首包签名再选解码器。
3. `.opus` 同理先辨认：若其实是标准 Ogg Opus，明确拒绝（否则会掉进 `OpusMemorySource` 报「容器长度异常」这种**症状话**）。
4. 新增 `NcOpusDecoder`：**包装引擎现成的 `OpusMemorySource`**（`null, null` = 不循环），只做 16bit PCM → float 帧；
   暂存按 `ScratchFrames` 预分配，`Read` 路径**零分配**（§六 纪律不破）。
5. `SniffOggCodec` 拆两层：「路径 → 字节」＋「**字节 → 编码**」（内层 `internal static` 收 `ReadOnlySpan<byte>`）——
   自检才能**喂内存里现造的最小 Ogg 页**，不必写测试文件（运行期禁止写临时目录，`AppPaths.cs` 硬约束）。

**行为差异（已知，非缺陷）**：新典 Opus 原生 48kHz（不是 44.1k），分析器按 `IVizFeed.SampleRate` 自适应；
`OpusMemorySource` 在构造期把整轨解进内存（≈22MB / 2 分钟曲），按键到出声有约 0.2–0.4 秒停顿。
