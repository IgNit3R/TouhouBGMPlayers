## 三、为什么非要有 `IVizHost`（方案 §3.6）

需求里有两条**离开主窗口根本写不出来**：「与宿主等高」「最大化时内嵌进宿主」。
隔离期没有主体 → 若照直写，这两条只能等 M6 才第一次跑到，等于把风险全压到接入那一刻。

把「主体」抽象成 `IVizHost`（只需 `IsAttached` / `State` / `Bounds` / `WorkArea` / `Changed`）之后：

- 判定逻辑 `VizPlacementLogic.Compute` 是**纯函数**，隔离期就能写完并被自检逐行覆盖；
- 隔离期挂 `FreeHost`（`IsAttached` 恒 false）→ 走 `Free` 分支，几何仍由窗口自己保管；
- 接入期只是把 `FreeHost` 换成 `MainWindowHost`（读主窗口的 `Left/Top/Width/Height` 与
  `SystemParameters.WorkArea`），**判定逻辑一行不动**。

判定表（＝ `VizPlacementSelfTest` 的用例表，逐行断言，实测输出见 §六）：

| 输入 | 结果 |
| --- | --- |
| `IsAttached=false`（自由模式） | `Free`，几何原样返回 |
| `Normal`，右侧空间 ≥ desired | `AttachedNormal`；`Left=host.Right`、`Top=host.Top`、`Height=host.Height` |
| `Normal`，`MinWidth ≤ 空间 < desired` | `AttachedNormal`；`Width=空间` |
| `Normal`，空间 < `MinWidth` | `Width=MinWidth`，`Left` 回夹到 `workArea.Right - MinWidth`（**宁可压住宿主，绝不跑出屏幕**） |
| `Maximized` 且内嵌 | `AttachedEmbedded`，`ShowAttachedWindow=false` |
| `Maximized` 且不内嵌 | 退化为贴右侧（预留开关） |
| `Minimized` | `ShowAttachedWindow=false`，几何不参与计算 |
| 期望宽度 < `MinWidth`（判定表外，补锁） | 按 `MinWidth` 办 |

⚠️ **「与宿主等高」只体现在 `Normal` 分支**：`Height = host.Bounds.Height`、`Top = host.Bounds.Top`。
这正是当初给附件窗口去掉标题栏的理由 —— 一条标题栏会白吃掉约 30px 的「等高」预算（M0 决策）。

## 四、「只拖右边缘 + 高度锁定」为什么走拦截 `WM_SIZING`（方案 §3.7）

| 路线 | 拖动表现 | 结论 |
| --- | --- | --- |
| **(i) 拦截 `WM_SIZING`** | 高度在调整**之前**就被改掉，无抖动 | **采用** |
| (ii) `ResizeMode` + `SizeChanged` 回写 | 拖高度时窗口先变大再被拉回，橡皮筋闪烁，且回写会再触发一轮事件 | 不用 |

`CorrectSize` 的三条规则：

1. **拖的不是右边缘 → 整条驳回**，返回当前矩形。上/下边缘与四个角都在此列 ——
   **「高度锁定」就是这么实现的**，不需要额外的"锁高度"标志位。
2. **拖的正好是右边缘 → 只放行 `Right`**，`Left/Top/Bottom` 按当前值钉死。
   拖右边缘本来就只改宽度；这里再把 `Top/Bottom` 显式钉一遍，是为了不依赖
   「系统不会乱提」这个假设（自检专门有一行「贴附·乱提高度」喂给它一个乱提的矩形）。
3. 宽度不得小于 `MinWidth`（**DIP 折算成物理像素**后再判：`lParam` 是物理像素）。

**P/Invoke 纪律**严格照 `src/Core/MediaKeysHotkey.cs`（项目唯一先例）：
`DllImport` 就地声明、拿到 HWND 后才 `AddHook`、**在 `Closing` 摘钩（不在 `Closed`）**、`Dispose` 幂等。
`VizWindow.Closing` 里的清理顺序据此改成 **① 摘钩 → ② 停节拍 → ③ 停声源**。

## 五、⚠️ 本轮最需要记住的一条：**钩子在隔离期是惰性的**

`VizWindowSizing.Attached` 在隔离期**恒为 false**（没有主体，`VizWindow.AttachedMode` 没人置位），
此时 `WndProc` 第一条判断就返回、**完全不插手** —— 窗口四边都能拖、高度也随用户。

这是对的做法（自由窗口本来就该这样），但后果要说清楚：

- **本轮能验证的只有纯函数 `CorrectSize`**（方案 §九 M3 的验收要求也正是这句话）；
- **实机拖动行为验证不到** —— 要等 M5/M6 把 `AttachedMode` 置位。届时拖右边缘应该「位置与高度都不动」，
  拖其它边应该**完全没反应**。这是 M5 的验收项之一，不是本轮漏做。

顺带一条踩过的：钩子的健壮性我最初断言成「未 Show 的窗口 `Attach()` 必须返回 false」，
实测确实返回 false，但那是 **WPF 内部行为**（`WindowInteropHelper.Handle` / `HwndSource.FromHwnd`
对未显示窗口的处理），拿它当契约太脆 → 改成断言**幂等**（重复 `Attach` 返回值一致）+
`Detach`/`Dispose` 可重复调用。**能不变红但随时可能翻的断言，比没有断言更糟。**

**同轮补的一处跨文件一致性**：「最小宽度 360」在 `VizWindow.xaml` 的 `MinWidth` 与
`VizPlacementLogic.MinWidth` 各声明了一遍。两处漂移的后果很隐蔽 —— 判定算出来的宽度会被
窗口自己的 `MinWidth` 顶回去，看起来像「判定算错了」。已加断言，实测一致（360）。

**自由模式几何持久化的证据**：机制在 M0 就落地了（`RestoreGeometry` ↔ `Closing` 回写），
本轮没有改动它。实证是用户自己的两次运行：`settings.json` 里的宽度先是 590、后来被拖成 360，
而 `CheckVizWindow` 每次都如实报出「尺寸 360×503」—— 说明「拖完关掉 → 下次按记住的值打开」这条链是通的。
