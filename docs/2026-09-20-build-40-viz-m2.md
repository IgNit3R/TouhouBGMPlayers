## 三、参数对照表（逐项对参照页 `.workbuddy/viz-demo/index.html`）

单位换算是 M2 最容易错的一处：参照页里**带 `d`** 的是 CSS px（= DIP，直接写数字），
**不带 `d`** 的是物理像素（要乘 `HairLine` = 1/DpiScale）。下表把两类的归属逐条列出。

### A 频谱条（`specDraw`）

| 参照页 | 归属 | 实现 |
| --- | --- | --- |
| `bw = SW/NB` | 比例，无量纲 | `slot = w / Bars` |
| `b*bw+1` / `max(1, bw-2)` | 物理像素 | `gap = 1 * HairLine`；`barW = slot - 2*gap`，下限 `HairLine` |
| `SH-4`（落地线） | 物理像素 | `bottom = h - 4 * HairLine` |
| `v[b]*(SH-8)`（满高） | 物理像素 | `span = h - 8 * HairLine` |
| `fillRect(0, SH-2, SW, 1)`（基线） | 物理像素 | `Rect(0, h - 2*HairLine, w, HairLine)` |
| 柱高 `v[b]` | —— | **不在这里算**，`VizAnalyzer` 算好放 `VizFrame.Bars` |

不做「最小柱高补偿」：参照页对很小的 v 就画一条亚像素柱，强行拉到 1px 会比参照页更响。

### C 电平 + J 相位（C/J 段）

| 参照页 | 实现里的常量 | 值 |
| --- | --- | --- |
| `my0 = 26*d` | `TopInset` | 26 |
| `my1 = H-64*d` | `BottomInset` | 64 |
| `mbw = 46*d` / `mgap = 30*d` | `BarWidth` / `BarGap` | 46 / 30 |
| `bx1-12*d` / `bx2+mbw+12*d` | `ScaleOverhang` | 12 |
| `bx1-16*d`、`ty+3*d` | `ScaleNumberRight` / `ScaleNumberBaseline` | 16 / 3 |
| `my0-8*d`（读数）/ `my1+16*d`（L/R 标签） | `ReadoutAbove` / `ChannelLabelBelow` | 8 / 16 |
| `ticks = [-36,-24,-18,-12,-6,0]` | `Ticks` | 同 |
| `ydb(db,y0,y1)` | `DbToY` | 超出量程**贴边**而非裁掉 |
| `#CEA86A` 余量段（`yv → y6`，`y6=ydb(-6)`） | `Warn` | -6dB 以上 |
| `jy = H-26*d` / `jy±4*d` / `jy±8*d` | `PhaseFromBottom` / `PhaseHalfHeight` / `PhaseAxisHalf` | 26 / 4 / 8 |
| `jx-1.5*d, jy±7*d`（指针） | `PhasePointerHalfWidth/Height` | 1.5 / 7 |
| 左右半槽**统一** `#2E2E31` | 无负半区特殊色 | 用户定稿「那个黄不要」 |

两处刻意的实现选择：
- **没有峰值帽 / 峰值保持线**（用户否决）。`VizFrame.PeakL/PeakR` 仍在算，暂时无人使用。
- **暂停语义**：`RmsL/R` 由分析器下落，`Correlation` 被压向 0，读数显示 `-inf`（`db <= -36`）。

`FormattedText` 用 `CultureInfo.InvariantCulture` —— 德语等区域会把小数点写成逗号，
而参照页是 JS 的 `toFixed`，永远是点号。

### D 利萨如（D 段）

| 参照页 | 实现 |
| --- | --- |
| `r = min(W,H)/2 - 8*d` | `r = min(w,h)/2 - 8`（8 带 d → DIP；已验算与参照页等价） |
| `px = cx + tdL[i]*r`、`py = cy - tdR[i]*r` | 同（纵轴用 R 且向上取正） |
| `NP=400`、`st = floor(2048/400)`、`i += st` | `Stride=5`、`PointCount=410`（**跳点而非平均**，照抄） |
| `lineWidth = max(0.75, d*0.6)` | `max(0.75*HairLine, 0.6)` |
| 十字轴 `#3F3F45`、`lineWidth=1` | `Grid` 画刷 + `HairLine` 粗细 |
| `if(actx && playing)` 才画轨迹 | `f.Active` |
| 覆盖色 `0.16`（播放）/ `0.05`（暂停） | `ActiveFade=0.84` / `PausedFade=0.95`（每帧保留系数） |

## 四、`VizFrame.Revision`：为什么非加不可

余辉是**按帧递推**的量（参照页每帧拿半透明底色盖一次），而我们的两个节拍并不同步：

```
渲染节拍 = CompositionTarget.Rendering = vsync        → 60 / 120 / 144 Hz 都可能
分析节拍 = VizAnalyzer 内部限频 = 固定 60 Hz          → 同一帧在 144Hz 屏上会被画 2～3 次
```

若余辉每画一次就推一格，**余辉长度会随刷新率缩水**（144Hz 上只有参照页的 42%）。
单看 `Active` 或 `Dt` 判不出来 —— 同一帧的多次绘制里这两个值完全一样。

所以 `VizFrame` 加一个单调递增的 `Revision`，**只有真重算分析时才 +1**，被限频挡掉的调用不动它。
`LissajousRenderer` 拿它当递推的触发条件：

```csharp
if (f.Revision != _seenRevision) { Advance(f); _seenRevision = f.Revision; }
```

自检把这条契约钉死了两处：
- `CheckVizAnalyzer`：首帧 `Revision >= 1`，**紧接的限频调用不许改它**；
- `CheckVizAfterglow`：同一个 `Revision` 连画两次，`TrailCount` 必须都是 1。

## 五、D 的余辉：一处刻意偏离原方案

方案 §199 的原文备注是「D：(L,R) 散点 + 余辉，0.6× 细线（**每宿主一份**）」，
实现时的任务描述里写的是「必须自己带一份历史位图（RenderTargetBitmap）做几何衰减」。
**实际选的是方案二**，理由与代价都记在这里，方便日后回改。

| 方案 | 语义保真 | 每帧开销 | 复杂度 |
| --- | --- | --- | --- |
| ① `RenderTargetBitmap` 乒乓 + 半透明覆盖 | **逐像素一致** | 同步渲染 + **回读**（面板越大越贵，UI 线程上扛着，WPF 里有名的坑）；尺寸变化要重建缓冲、历史会丢 | 高（双缓冲、DPI/尺寸同步） |
| ② **历史图层**（已选） | 单条笔画经过的像素**完全同值**（都是 `0.84^τ`）；反复经过的像素两边都饱和到全不透明；差异只在抗锯齿的半覆盖像素上 | 20 次 `DrawGeometry` + 20 个几何对象/帧，**零回读、零 GPU 往返** | 低（无外部资源，尺寸无关） |

选 ②。若哪天观感真的对不上，回改成 ① 只需换 `LissajousRenderer.cs` 一个文件 ——
面板、帧契约、其余三个渲染器都不用动。

配套的两个小设计：
- **透明度量化 32 档**，把一个透明度烘进画刷的画笔缓存下来（`Brush.Clone()` + `Opacity`），
  每帧一次分配都不做。用克隆而不是拆 `SolidColorBrush.Color` 拼 ARGB，是因为主题画刷未必是纯色，
  且 `VizStyle` 立的规矩是「一个十六进制字面量都不留」。
- **恢复播放时不清空历史**。清空会让快速暂停/恢复时余辉整体闪一下；透明度是**绝对值**，
  暂停期间旧层早已暗到看不清，恢复后继续按同一系数衰减，不会突然满亮。

### 6.1 `CheckVizRender` 重写成「离屏验像素」

M1 那版只验「不抛异常」，这能骗过人：渲染器早退、几何建空、画刷全透明，都是**静默空白**。
M2 改成用 `RenderTargetBitmap` 离屏渲染，逐像素检查：

1. **不抛异常** —— 两个尺寸各一次（320×160 与 120×40，覆盖面板被拉扁时的夹取分支）；
2. **真的出了像素** —— 左上角必须是底色（顺带证明离屏位图真的渲染了，若全空通道会是 0x00，会被这条抓住而不是误判成「画了很多」）；
3. **画面必须随信号变化** —— 「有信号的帧」与「全零的静止帧」各画一遍，**两幅图直接逐像素比**，
   变化量 ≥ `max(64, 静止态非底色像素 / 10)`。静止态配一个**全新的渲染器实例**
   （D 有跨帧状态，复用会把上一轮的余辉算进来）。

第 3 条是这一轮最值钱的断言：它把「FFT 算对了但柱高压成 0」「RMS 算对了但没画出来」
这类**数值正确、画面错误**的回归从「靠眼睛看」变成「自检报红」。

⚠️ 第 3 条最初写成「比较两者**各自与底色**的差异像素数」，在 C+J 上**假失败** ——
详见 §7.4（电平柱画在自己的底槽里，是"改色"而不是"从无到有"，那个度量看不见）。
**结论：验「有没有响应输入」要两幅输出直接比，不要各自与基准比。**

### 6.2 `CheckVizAfterglow`：唯一带状态渲染器的状态机

只断言 `TrailCount`（新增的诊断属性，不参与绘制），五步：

| 步骤 | 期望 | 抓什么 |
| --- | --- | --- |
| 首帧（`Active`） | 1 | 递推起不来 |
| 同一个 `Revision` 再画一次 | **仍 1** | 余辉跟着 vsync 推（144Hz 上余辉缩水） |
| 再推 3 个新 `Revision` | 4 | 递推没累积 |
| `Active=false` 连推 120 帧 | **0** | 淡影灭不干净（`0.95^120 ≈ 0.002 < 1%` 阈值） |
| 恢复播放 | 1 | 旧影复活 |

### 6.3 `CheckVizLayout`：把「从截图量比例」换成**布局实测**

M0 量分区比例是拿截图逐行找边界线做的，当时**肉眼先估成 3.9:1，实际 2.25:1，差了 70%**。
现在不必了：`RenderPixels` 已经证明 `Measure/Arrange` 能在离屏跑起来 ——
不必 Show 窗口（`ShutdownMode=OnLastWindowClose`，乱开窗口会把进程提前关掉），
直接对窗口内容根元素排版，再读 `ColumnDefinition.ActualWidth` / `RowDefinition.ActualHeight`。

为此给 XAML 补了三个 `x:Name`（**只为自检服务，不改任何观感**）：
`GroupFirst` / `GroupSecond`（两个组的 Grid）/ `LeftColumn`（第一组左列那个嵌套 Grid）。

⚠️ **列定义在 `GroupFirst` 上，行定义在 `LeftColumn` 上** —— 两者不是同一个 Grid。
第一版把两个都往 `GroupFirst` 上读，`RowDefinitions` 是空的 → 抛 `ArgumentOutOfRangeException`。

- **硬断言**：组比 2.3 : 1、列比 7 : 3、A : B = 1 : 1、D : 封面 = 1 : 1（容差 3%）、

## 七、踩到的坑

### 7.1 同一文件的多个编辑并行发出会互相覆盖（**已产生过一次坏文件**）

（`StaticResource` 是加载期解析的）。真正会暴露它的是 `CheckVizWindow`（构造期炸）。

对策：**同一文件的多个改动串行发出，改完通读一遍**。M2 收尾时就是这么修回来的
（D 块 → 头部注释 → B 段注释，一次一处）。

### 7.2 余辉的节拍错配（设计期发现，未进 build）

见 §四。这是「渲染跟 vsync、分析限 60Hz」这条已定语义**顺带带出来的**新约束 ——
M1 的三块渲染器都是无状态纯函数，撞不到；D 一上来就撞上了。

### 7.3 CS0136：内层 `for (int k …)` 遮蔽了外层的 `float k`（**build 第一次就报**）

```
src\Viz\Renderers\LissajousRenderer.cs(173,22): error CS0136:
无法在此范围中声明名为"k"的局部变量或参数，因为该名称在封闭局部范围中用于定义局部变量或参数
```

`Advance()` 里 `if (f.Active) { for (int k = 0; …) … }` 的 `k` 落在 `if` 块内，
而方法体后面又有一个 `float k`（暂停分支的衰减系数）。C# **不允许内层局部遮蔽外层局部**
（这是错误不是警告）—— 与 C++ 的直觉相反，也和"这两个 `k` 看着八竿子打不着"的直觉相反：
判定只看**声明所在的嵌套层级**，跟"用不用得上"无关。

改法：暂停分支那个改名为 `fade`（顺带更达意）。

⚠️ 这类错误的特征是**同一个字母在方法的不同深度各用一次**。以后在同一个方法里，
`for (int i…)` / `for (int k…)` 的循环变量哪怕只活三行，也要跟方法体里的局部变量错开名字。

⚠️ **同日又踩了一次**：`VizSelfTest.CheckVizAdaptiveBars` 里方法体上层有 `bool centered`，
新加的参数扫描内层又写了 `double centered` → 同一个 CS0136。
可见这条规则光「知道」不够，得当成写循环时的检查项：**内层作用域里的新名字，先扫一眼外层有没有同名的**。

### 7.4 「与底色不同的像素数」看不见「在已上色区域内部改色」（**断言假失败**）

第一轮自检 9 / 10，唯一失败项：

```
[FAIL] 四个渲染器端到端（离屏出像素 + 有信号多于静止）
       A 频谱条 亮 1825 / 静 320；B 示波器 亮 5513 / 静 1961；
       C+J 电平相位 亮 9244 / 静 9271 ← 有信号没多画东西；D 利萨如 亮 910 / 静 572
```

**读起来像「C+J 的电平柱没画出来」，实际不是。** 电平柱是画在**自己的底槽**里的 ——
底槽（`Track` 色）**本来就不是底色**，柱体只是把那块区域的**颜色**从 `Track` 换成 `Bar`，
「与底色不同的像素数」因此**一个都没多**（两边的差 27 像素全是读数文字 `-inf` 与 `-4.9` 的笔画差）。

**度量本身的盲区**：`painted = 数「与底色不同的像素」` 只能看见「从无到有」，
看不见「在已上色区域内部改色」。C 的电平柱、A 的余量色段、任何"槽 + 填充"式的画法都撞在这一点上。

**改法（改断言，不改渲染器）**：把「两者各自与底色比」换成**两幅图直接逐像素比**，
门槛取 `max(64, 静止态非底色像素 / 10)`。修后：

```
A 频谱条 变化 1505 / 门槛 64；B 示波器 变化 4826 / 门槛 196；
C+J 电平相位 变化 5977 / 门槛 927；D 利萨如 变化 346 / 门槛 64
```

C+J 的 5977 与「2 根柱 × 46 宽 × 58 高 ≈ 5365 + 文字差」逐项吻合 ——
**反证了柱体一直都在画**。这条新度量还顺带把语义拧正了：要验的是
「**画面有没有响应信号**」，而不是「有没有多画东西」。

⚠️ 教训入清单：**验证「有没有响应输入」时，永远比"两幅输出"的差，别比"各自与基准"的差** ——
后者在「基准本身也是被绘制物的一部分」时会静默失效。

### 7.5 布局自检量出来的既有缺陷：**C+J 面板宽度不够**（已按 A 方案修好）

这不是 M2 引入的，是 M2 的渲染器接上去之后才**显形**的（M0/M1 那块是占位文字，多窄都无所谓）。

`LevelPhaseRenderer` 的几何是从参照页整段抄来的，而参照页那块画布**本来就 ≥194 DIP 宽**。
我们的窗口按 7:3 分栏后右列只有：

| 窗口总宽 | C+J 面板宽 | 够不够（需 194） |
| --- | --- | --- |
| 560（XAML 默认） | 161 | ✗ 窄 33 |
| 590（用户此前记忆值） | 170 | ✗ 窄 24 |
| **360（用户当前记忆值）** | **101** | ✗ 窄 93 |

**症状分级**（都是算出来的，不是看图看出来的）：
- 宽度 170 左右时：**刻度数字被左边缘裁掉**。刻度的右边界画在 `bx1 - ScaleNumberRight`，
  数字右对齐在那儿 → 宽度不够就先丢最左边那几位（「-36」显成「6」、「-12」显成「2」）。
  刻度是这块面板**唯一的量纲信息**，裁掉等于读不出电平。
  （用户那张实机截图里 C 区左侧只剩零星的「2」—— 正是 -12 / -24 的尾巴。）
- 宽度 101 时：`bx1 = 101/2 − 15 − 46 = **−10.5**` → **两根电平柱本身各有约 10px 被裁**，
  J 横条的左端也出界 22px。即「窗口拉到最窄」时电平表是坏的，不只是刻度看不见。

判定入口：让渲染器自己声明宽度阈值，布局自检只负责对一下 —— 现在是两个：
`LevelPhaseRenderer.ReferenceWidth`（**194**，与参照页逐像素一致的宽度）与
`MinWidthWithNumbers`（**109**，还能保住刻度数字的宽度）。

**三条修法**（改前留档；用户 2026-09-20 选 **A**）：

| 方案 | 做法 | 成本 | 副作用 |
| --- | --- | --- | --- |
| **A · 渲染器自适应**（推荐） | `LevelPhaseRenderer` 按可用宽度等比缩 `BarWidth`/`BarGap`/外伸；宽度还不够就**放弃刻度数字**只留刻度线（柱顶已有 dB 读数）。宽度 ≥194 时**与参照页逐像素一致**（自适应是 no-op） | 只动一个文件，≈25 行 | 窄面板下柱体比参照页细 |
| B · 加宽窗口 | 把 `VizWindow` 的默认 `Width` 与 `MinWidth` 抬到 ~650（保证 C+J ≥194） | XAML 两行 | 窗口**不能拉窄**；会覆盖用户当前 360 的记忆值 |
| C · 改柱体几何 | `BarWidth 46→30`、`BarGap 30→22`、`ScaleNumberRight 16→10` → 需求降到 142 | 常量几行 | 全尺寸下都偏离参照页；**且救不了最窄窗口**（101 仍不够） |

### 7.6 A 方案落地：`LevelPhaseRenderer` 横向自适应

把「几何抄参照页」改成「**先算可用宽度，再摆位置**」，三条优先级从硬到软：

1. **柱体与刻度线不许越界** —— 硬约束，任何宽度都成立（这是叫「自适应」而不是「够宽才行」的原因）；
2. **尽量保住刻度数字**（唯一的量纲），但压在下面时不让柱子细过参照页的一半
   （`MinBarScaleWithNumbers = 0.5`，对应阈值 109）；
3. **尽量接近参照页几何**：宽度 ≥ `ReferenceWidth`（194）时缩放系数 `s = 1`、柱体居中
   —— **自适应是 no-op，与参照页逐像素一致**。

摆位只用一行：**`BarA = max(居中位置, 左侧需求)`**。

- 宽裕 → 居中位置更大 → 居中（参照页行为）；
- 紧张 → 贴住左侧需求（刻度数字只占左边），把**右侧的富余也用上**（右边只要 12px 刻度外伸）。

换成算式就是：`avail = w − leftNeed − ScaleOverhang`，`s = min(1, avail / 122)`，
柱宽/间距按 `s` 等比缩。降级阶梯：`w ≥ 194` 原样 → `109…194` 柱体缩、数字留住 →
`< 109` **放弃数字**、柱体吃满（柱顶的 dB 读数仍在，量纲不至于丢）。

#### A1 · 用户实机截图又暴露一处同类问题（同日补修）

用户把窗口拉到最小后截图，C 区本身已经正常（读数 `-14.8 / -14.2`、底槽、L/R 标签都在，柱子没出界），
但 **J 相位横条的端点刻度只剩「1」「0」「+」** —— `-1` 的负号与 `+1` 的末位被裁掉了。

根因同 §7.5：`-1` / `+1` 是**居中**画在横条两端的（`jx0`、`jx1`），面板一窄横条就贴到面板边缘，
居中的双字符标签必然各裁掉半个。

修法是统一一条规则 —— **文字放得下就居中，放不下就往里挪到贴边**：

```csharp
internal static double FittedLeft(double textWidth, double centerX, double panelWidth)
{
    double left = centerX - textWidth / 2;
    if (textWidth >= panelWidth) return (panelWidth - textWidth) / 2;   // 面板比字还窄：无解，居中
    if (left < 0) return 0;
    if (left > panelWidth - textWidth) return panelWidth - textWidth;
    return left;
}
```

全部居中文字都改走它：电平读数、L/R 标签、J 的相关读数与三个刻度。
① 宽裕时与原来的居中**逐像素一致**（不是妥协，是同一条规则的退化分支）；
② 101 宽时按 Consolas 11 实测字宽算：`-1` 落 `0…9.5`、`+1` 落 `88.9…101`，都完整可见。

⚠️ **这类问题的正确验法是几何，不是像素** —— 像素检查**分不出「贴边」与「被裁」**（两者都碰到边缘）。
所以位置计算抽成纯函数，自检对 **66035 组参数**扫一遍，断言：① 放得下时必在界内；
② 合法居中解不许被改动（这条同时守住了「宽裕时与参照页一致」）。

**新增第 10 项自检 `CheckVizAdaptiveBars`**：这条契约是**纯几何、无副作用**，所以不靠肉眼看画面，
直接对 `ComputeLayout(w)` 扫 40→600 每个整数宽度，断言：

- 越界量恒为 0（`SpanLeft ≥ 0` 且 `SpanRight ≤ w`）；
- 柱宽/间距为正、两柱不重叠；
- 宽度 ≥194 时必须保留数字；
- 宽度 ≥194 时几何与参照页一致**且居中**（证明 no-op 这一半没写坏）；
- 保留刻度数字时左侧必须真的腾得出来（`BarA ≥ ScaleNumberRight + ScaleTextWidth`，
  这是 §7.5 那个缺陷的根因）；
- **⑥ 真画一遍**：最窄的实际面板尺寸 **101×343**（窗口拉到最小时 C+J 的宽 × 第一组的高）
  渲染出来必须真的变了 —— 几何算对了不等于画出来了，这是 §7.4 那条教训的同一个意思；
- **⑦ 文字贴边钳制**（A1）扫 66035 组参数，见上。

实测（12 项全绿）：

```
最大越界 0px（须 0）
柱宽  101→29 / 150→38.5 / 170→46 / 194→46 / 400→46
刻度数字保到宽 109（阈值 109）
≥参照页宽度：居中且几何一致（自适应为 no-op）
最窄实际尺寸 101×343：变化 12615 像素（门槛 1688）
文字贴边钳制 66035 组参数：全在界内且不改变合法居中解
```

⚠️ 注意 **170 时柱宽已经是 46（参照页原值）** —— 这就是「用上右侧富余」的效果：
如果坚持居中，同样的宽度下柱子只能到 37。用户此前 590 宽的窗口正好落在这里，
**所以那次实机截图里的柱子尺寸本来就是对的**，坏的只有被裁的刻度数字。

`BarLayout` 结构体与 `ComputeLayout` 是 `internal` 的 —— **只为自检暴露**，绘制路径解构一次即用。
