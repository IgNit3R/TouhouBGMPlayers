## 三、纠正一处说法：「免分配」应为「免元素分配」

那张表的备注原文是「**推荐**，免分配、纯 retained-mode」。**「纯 retained-mode」准确，
「免分配」不准确** —— WPF 每录一条绘制指令都要分配一个指令对象，几何数据也要缓冲。
准确的表述是：**免的是「元素分配」**（`Polyline` 是 `UIElement`，每帧增删会牵动属性系统、
布局失效、渲染树与命中测试列表重建），**不是零分配**。

⚠️ 但**「免元素」不等于「开销就低到可以不管」** —— 几何数据本身照样是每帧分配。
D 的旧做法实测 **382KB/帧**（≈23MB/s）就是明证。原文已改。

## 四、两处优化（都是内部改动，观感不变）

### 4.1 D 利萨如：几何从「每帧 20 条」改成「槽位索引复用」

**关键在索引的是「槽位」而不是「age」**：槽位里的点只在被写入的那一帧才变，所以
**每帧只需重建「刚写进去的那一个」**（20 → 1）。按 age 索引会每帧全废，白忙一场。

- 几何按槽位缓存（`_geos[slot]`）＋ 一个 `_geoDirty[slot]` 标记；`Advance` 写入后标记该槽过期。
- **面板尺寸一变整盘作废**（几何是按中心/半径投影出来的），故记下建它时的尺寸 ——
  这只发生在用户拉窗口那一瞬间。
- 用「整条重建」而不是「`Clear` + 重填」：几何冻结后不能再改，而冻结能让渲染端缓存它；
  重建一条只多一个对象，却省掉可变几何在已录制内容里被改动的那类麻烦。
- **20 次绘制指令没变**（每层 alpha 不同，必须分开画），变的是几何数据。

**对照实测**（自检里跑同一套循环，只切 `DisableGeometryCache`）：

```
关掉缓存 382.1KB/帧  →  开启 22.4KB/帧（降到 6%）
```

那个 `DisableGeometryCache` 是 **internal、仅供自检** 的开关 —— 没有对照，
「省了」只是一句话而不是数字。

### 4.2 C+J：会变的读数文字按字符串缓存

自检量出 **C+J 是四个里最高的（33.7KB/帧），而它一条几何都没有** ——
因为它每帧新建 3 个 `FormattedText`（两个电平读数 + 一个相关读数），
而 `FormattedText` 的构造要走一遍文本排版。

按字符串缓存后：**33.7 → 26.8KB/帧（−20%）**。⚠️ 只降了 20%，说明
**剩下的大头不是 `FormattedText` 构造，而是每帧 14 次 `DrawText` 各自的 glyph run**
—— 见 §六 的下一步。

缓存天然有界：电平读数只可能是 `-inf` 或 [-36,0] 的 1 位小数（≈360 种），
相关读数只可能是 [-1,+1] 的 2 位小数（≈200 种）；另加 1024 条上限兜底
（万一削顶后 dB > 0 也不至于让它无限长）。DPI 变化时整盘清掉。

## 五、新增第 18 项自检：`CheckVizAllocation`

```
[ ok ] 每帧分配字节数（渲染路径，含 WPF 指令对象）
       A 频谱条 0.9KB/帧；B 示波器 17.7KB/帧；C+J 电平相位 26.8KB/帧；D 利萨如 22.4KB/帧；
       D 槽位缓存对照：关掉 382.1KB → 开启 22.4KB（降到 6%）（320×160，预热 60 帧后量 300 帧）
```

做法：`GC.GetAllocatedBytesForCurrentThread()` 包住 N 次 `panel.Redraw()`，除以帧数。

- **不预热不计**：预热 60 帧，让 `EnsureResources` / JIT / WPF 内部的一次性分配先发生；
- **每帧都 ++Revision**：像真机一样，否则 D 会「没有新数据」而不做它该做的事，量出来是假的；
- **刻意不走 `RenderTargetBitmap`**：那会把合成开销混进来，看不清我们自己这一层；
- **度量含 WPF 内部**的分配（`RenderOpen()` 的指令对象就在里面）——这正是关心的量：
  「每帧往 gen0 丢多少垃圾」。

**上限的定位**：取实测 ×~1.3，**不是性能目标，是用来抓回归的**。
绝对值不是重点，**跨版本可比才是** —— 谁把 D 的槽位复用改回每帧新建 20 条，
数字会直接跳 17 倍、断言立刻红。

## 六、C+J 的文本：静态层（**已做** —— 本轮第二阶段）

**做法**：把 C+J 拆成**静态层 + 动态层**。

- **静态层**（冻结的 `DrawingGroup`，缓存键 = 面板尺寸 + DPI）：背景、两根底槽与 L/R 标签、
  6 条刻度线与刻度数字、J 的左右半槽/中轴/端点刻度 ——
  每帧一条 `dc.DrawDrawing(层)` 代掉二十来次绘制（其中 **11 次是会分配 glyph run 的文字**）。
- **动态层**：余量段、柱体、两处读数、J 的指针。
  ⚠️ 指针必须画在静态层**之后** —— 它要压在 J 的中轴上面。
- **拆分依据**：静态的那些**都不与柱体/指针重叠**（标签在 `my1` 之下、刻度数字在两柱左侧、
  J 的槽在中轴上下），所以提前画不会被遮住 —— 与原来的绘制顺序**视觉等价**。
- 排版算一次（`Metrics`）往下传，两层共用 —— 分头算迟早会漂。

**实测：26.8 → 9.1KB/帧**（比预估的 ~8KB 还略好）。

**等价性证据**：`CheckVizRender` 里 C+J 的「有信号 vs 静止」变化像素，**改前改后都是 5977，一模一样**
—— 重构没动一个像素。这比"看着一样"硬。

⚠️ **代价**：拖动窗口时每帧尺寸都在变 → 每帧都要重录静态层，那一刻比原来还贵一点。
拖动是瞬态、稳态才是日常，这个交换划算。

### B / D 为什么不做同样的处理

它们的静态部分只有 3~6 个图元、且**几乎不含文字**（B 的分割线/中线/两个标签、D 的两条轴），
省下的量级（估 1~3KB）不值得再多一层缓存失效。
**它们的开销主体是折线点数据** —— 那是「每帧重画一条折线」的固有代价。

### 全部四块的最终账

| 渲染器 | 每帧分配 | 主要构成 |
| --- | --- | --- |
| A 频谱条 | **0.9KB** | 53 条矩形指令（≈地板） |
| B 示波器 | **17.7KB** | 2 条折线的点数据。⚠️ `StreamGeometry.Clear()` **会放掉内部点缓冲**，
所以「复用」省下的只是包装对象（几百字节）——这笔压不下去 |
| C+J 电平相位 | **9.1KB** | 静态层已抽出；每帧剩 5 次矩形 + 3 次文字（两处读数 + 指针） |
| D 利萨如 | **22.4KB** | 1 条几何（410 点）+ 20 条绘制指令 |
| **合计** | **≈50KB/帧** | ≈**3MB/s** @60fps（改前 ≈435KB/帧 ≈26MB/s） |
