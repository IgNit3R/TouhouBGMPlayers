## 0. 结论摘要

**可行，且成本比看起来低；但真正的活儿不在"把字符串抽出来"。**

1. **盘点结果**：全项目用户可见文案共 **248 条**。其中界面层 177 条（XAML + 三个代码搭的对话框 + MainWindow 的代码赋值），业务/解码层 **71 条**。
2. **真问题**：那 71 条里有 34 条是 `Core/PathValidator.cs` **直接产出中文展示文案**（"目录不存在"、"缺少补丁容器 X"、"作品号不符：文件是 TH13…"），另有 37 条是 `Audio/*` 抛出的异常消息 —— 这些最终都被 `MessageBox.Show(this, ex.Message, …)` 原样端到用户面前。
   **不改这 71 条，本地化就只是把文案从 .cs 搬到一个文件里，边界依旧会渗。**
3. **路线**（2026-09-19 已定，见 §4.5）：新增独立类库 `ThbgmPlayer.Localization`（`net10.0`、零 WPF 依赖），资源以 **JSON 内嵌 + 程序目录 `lang\` 可选覆盖** 承载；结构层改为产出「状态码 + 参数」，文案统一由该层在 UI 边界处解析；**语言在设置页手动选、立即热切换**。
4. **三步走**：① 抽取但零行为变化 → ② 结构层状态码化 → ③ 日语翻译与宽度适配。第 ① 步做完必须能在"只有 zh-Hans"时逐字复现今天的界面，这是回归基线。
5. **热切换是四条决策里代价最高的一条**：它把"改文案"变成"改文案 + 改刷新时机"。真正的工作量不在 `DynamicResource` 本身，而在 §4.6 列出的那批**算出来的文本**必须补上重算入口。
6. **切换范围分两条通路**（§9）：**外壳多语言**（UI 文案、播放列表的界面文案 → `lang/*.json`，键是 key）与**内容多语言**（曲名、乐评、作品名 → 数据层，键是 `gameId + musicNo`）。内容**绝不能进 `lang/`**。另：乐评区（§9.4）在现有设计与代码里**零痕迹**，它是**新功能**而非本地化项。

## 2. 分界线：哪些**不能**进资源

这一节是"分离 localization"能不能成立的前提。分不清，"分离"就会退化成"又多一层间接"。

### 2.1 明确不进（内容）

| 字段 | 来源 | 理由 |
|---|---|---|
| `TrackDef.Title` | musiccmt.txt / bgminfo 原始日文 | 硬约束 §1.4：曲名一律日语原名，不显示译名 |
| `GameDef.Name` | 各作 `おまけ.txt` 首行 | 同上，官方日文原名 |
| `GameDef.ShortName` | `Name` 按 `〜`/`～` 切分（`TrackIndex.cs:143-154`） | 派生自 Name |

**这是本方案最有力的根据**：内容层本身就与界面语言无关，所以"把 UI 文案全部上移到一个独立层"不会有任何跨层耦合。反过来，如果曲名也要跟着语言变，这个方案就不成立。

### 2.2 灰度区：副版标签

`GameDef.MainLabel` / `AltLabel`（`TrackIndex.cs:116-117`）是**索引里数据驱动**的按钮文字：TH13 是「霊界版」，新典是「新典 / 原典」。它们是日文词，中文用户也直接读得懂。

**建议**：一期**不动**，保持数据驱动原样。若将来要翻，扩展点是在索引 JSON 里加 `lm_zh` / `la_zh`，而不是丢进 UI 资源表 —— 因为它属于"作品元数据"而不是"界面外壳"。

### 2.3 顺手捞出来的一个坑：导出文件名

```csharp
// src/Audio/WavExporter.cs:38
name += "_" + (game.AltLabel ?? "灵界版");
```

导出产物文件名里带了「灵界版」。如果 UI 语言可切，必须明确：**文件名不跟随 UI 语言**。理由是它是数据产物——可能被脚本消费、被用户按名检索、跨语言共享的一份导出不该有两套文件名。建议固定为 `AltLabel ?? "霊界版"`（顺手把简体字改成日文原名，与内容层一致）。

同理，`PlaylistStore` 的默认名 `列表 {i+1}` 和 `MainWindow.xaml.cs:1462` 的 `我的列表 {i}` **会落盘到 playlists.json**。已经存下的名字不会因为切语言而变——这是对的，但要写进规格里，免得被当 bug 报。

## 3. 目标架构

核心思路一句话：**结构层不再产出用户可见文本，只产出「码 + 参数」；文案在 UI 边界处一次性解析。**

### 3.1 "分离出去"的三种含义

用户说的"分离"，实际包含三件事，难度和收益完全不同：

| 层次 | 含义 | 价值 |
|---|---|---|
| (a) **工程分离** | 新建 csproj，文案资源成为一个独立程序集 | 中：编译边界清晰，可整体交给翻译者 |
| (b) **文件分离** | 文案集中在 `lang/*.json`，与代码物理分开 | 中：非程序员可改 |
| (c) **职责分离** | Core/Audio 不再产出展示文案 | **高**：这才是"渗漏"的根治 |

(a)(b) 是搬运，(c) 是重构。**建议三件一起做，但第 (c) 件才是重点**——只做 (a)(b) 的话，`PathValidator` 那 34 条仍然会在业务层产中文，将来加英文就得到处补 if。

### 3.2 目标结构

```
src/
  Localization/                    ← 新增独立类库，net10.0（不带 -windows）
    ThbgmPlayer.Localization.csproj
    Loc.cs                         查找 / 格式化 / 切换语言，约 80 行
    LocKeys.cs                     key 常量（由 tools/gen_lockey.py 从默认 json 生成）
    Lang/
      zh-Hans.json                 内嵌为 EmbeddedResource
      ja.json                     内嵌为 EmbeddedResource
  UI/
    LocExtension.cs                WPF 侧桥接（MarkupExtension / ResourceDictionary 投影）
  ...
ThbgmPlayer.exe
lang/                              ← 可选，运行时覆盖（社区加语言 / 临时改词）
  ja.json
```

对外只暴露三个入口，其余全私有：

```csharp
Loc.S(LocKeys.Menu.Settings)              // 取串
Loc.F(LocKeys.Path.StatusNotSet)          // 带占位符 {0}
Loc.Apply(new CultureInfo("ja"))          // 切换（重启或重建窗口后生效）
```

### 3.3 结构层的改造形态

**PathValidator（34 条）**：`ValidateResult` 目前 `Message` 是给界面看的字符串。改成：

```csharp
// 现在
return ValidateResult.Fail($"作品号不符：文件是 TH{actualMajor}，这里应为 {game.Code}");

// 改后 —— 结构层只给码和参数
return ValidateResult.Fail(PathIssue.GameCodeMismatch, actualFam, game.Code);
```

`PathStatus` 枚举已经存在（`NotSet / Ok / Warn / Fail`，`PathValidator.cs:29`），所以这个改动是**顺着既有设计往前走一步**，不是另起炉灶。UI 侧在 `SettingsWindow.xaml.cs` 那个 `StatusText` 映射处（:85 附近）统一解析。

**异常（37 条）**：分两类处理，不要一刀切。

| 子类 | 例子 | 处置 |
|---|---|---|
| 用户能不能做点什么 | 「未设置 th13 的路径（设置 → 路径）」、「找不到 data\xxx」 | 转错误码 + 参数，在 `catch` 处本地化 |
| 纯诊断 | 「新典 Opus 第 3 条记录的包长声明为 480，应为 488（容器损坏或版本不符）」 | **保持不动**。它只在真出问题时出现，是给开发者/上报用的证据 |

这样需要本地化的异常从 37 条压到大约 15 条，键表不会爆炸。这是务实的分界线。

## 4. 选型决策

> 2026-09-19 已定：资源载体 = B（内嵌 JSON + `lang\` 覆盖）；切换方式 = 手动选 + 立即热切换；结构层 = 二分法。
> 本节记录选项与理由，§4.6 是热切换的落地清单。

### 4.1 资源载体 —— 【已定】B：内嵌 JSON + `lang\` 可选覆盖

| 方案 | 产物 | 翻译者体验 | 加语言 | 编译期校验 |
|---|---|---|---|---|
| A. resx + 卫星程序集 | 多出 `ja\ThbgmPlayer.Localization.resources.dll` 子目录 | 最好（VS/Rider 有编辑器） | 要重编译 | 强（生成的 Designer 类） |
| **B. 内嵌 JSON + 程序目录覆盖** | **零子目录**，仍是一个扁平文件夹 | 直接改文本文件 | **放个文件就行** | 弱，需校验脚本 |
| C. 单工程内 resx | 同 A | 同 A | 要重编译 | 强 |

**选定 B**，理由和本项目的既有气质高度一致：

- DESIGN_v3 §2 的产物清单是**扁平的**（exe + 几个 dll + settings.json + favorites.json + playlists.json + export\）。加 `ja\`、`zh-Hans\` 两个子目录，与"一个文件夹跑"的干净感相悖。
- 项目**已经有 `tracks.override.json` 这个"可选外置覆盖"先例**——B 方案就是同一套模式，用户认知成本为零。
- 东方同人生态里，"放个文件就能加语言"比"装 VS 改 resx"现实得多。翻译者往往是非程序员。
- 代价（无编译期校验）用 `tools/check_loc.py` 补回来——项目 `tools/` 下已有 19 个 py 脚本，这是既有习惯。

被放弃的 A 的代价是发布目录会多出 `ja\`、`zh-Hans\` 两个子目录，与扁平布局相悖。

### 4.2 语言切换 —— 【已定】设置页手动选 + 立即热切换

| 方案 | 说明 | 结论 |
|---|---|---|
| 跟随系统 + 覆盖，重启生效 | 改动最小，无状态同步问题 | 未选 |
| 手动选 + 重启生效 | 同上，只是不自动 | 未选 |
| **手动选 + 立即热切换** | 体验最好；代价见 §4.6 | **选定** |

**存储**：`AppSettings.Ui` 增加 `language` 字段，取值 `"auto"` / `"ja"` / `"zh-Hans"`，切换后立即 `Save()`。`AppSettings.Version` 不用动——加字段是向后兼容的，旧 settings.json 读进来就是 `"auto"`。

**热切换的机制骨架**（三层，缺一不可）：

1. **资源层**：`Loc.Apply(culture)` 重新加载 JSON，重建那个 `ResourceDictionary`，替换 `Application.Current.Resources.MergedDictionaries` 里的旧条目。
2. **声明式 UI**：XAML 里所有文案改用 `{DynamicResource L.xxx}`（**不能是 `StaticResource`**，静态资源在加载时就固化，不会重解析）。
3. **代码构筑的 UI 与算出来的文本**：走 `SetResourceReference()`（代码版的 DynamicResource）+ 显式重算入口。见 §4.6。

### 4.3 结构层范围 —— 【已定】二分法

用户能采取行动的文案转错误码（约 15 条），纯诊断的 22 条保持原样。理由见 §3.3。

### 4.4 其余（未定，待确认）

- **中性资源语言**：放 zh-Hans（最小惊讶）还是 ja（贴合项目气质）。
- **`MessageBox` 系统按钮**：WPF 的 `MessageBox` 由系统绘制，「确定 / 是 / 否 / 取消」跟随 **Windows 系统语言**，不跟随应用语言。热切换选下去之后这个不一致会更显眼（应用已是日语、按钮还是中文）。一期建议**接受并记录为已知行为**；根治要用自绘对话框替换 `MainWindow.xaml.cs` 里约 10 处 `MessageBox.Show`，那是独立的一件事。

### 4.5 已定方案速览

| 维度 | 决定 |
|---|---|
| 程序集 | 新增 `src/Localization/ThbgmPlayer.Localization.csproj`，TFM `net10.0`（不带 `-windows`），零 WPF 依赖 |
| 资源形态 | `Lang\zh-Hans.json`、`Lang\ja.json`，`EmbeddedResource` 打进程序集 |
| 外置覆盖 | 程序目录 `lang\<culture>.json` 存在则整体覆盖内嵌值 |
| 语言选择 | `AppSettings.Ui.language` = `auto` / `ja` / `zh-Hans`，设置页「外观」内切换 |
| 生效时机 | 立即热切换，同帧内所有窗口重绘 |
| 结构层 | 产出「状态码 + 参数」，零列表展示文案 |
| 异常 | 二分：用户可见的转错误码（约 15 条），诊断保持原样（约 22 条） |
| 内容层 | 曲名 / 作品名 / 副版标签**一律不动** |

### 4.6 热切换的落地清单

热切换的真实工作量**不在 `DynamicResource`，在"算出来的文本"**。把项目里的文本按产生方式分三档：

**第 1 档 · 声明式（XAML 属性）——改法是机械的**

| 位置 | 改法 | 备注 |
|---|---|---|
| `MainWindow.xaml` Title / 菜单 Header / 按钮 Content / ToolTip / 标签 Text | `{DynamicResource L.xxx}` | 注意菜单里 `_S` 这种加速键是值的一部分，跟着资源走 |
| `MainWindow.xaml:156-160` DataGrid 列头 | ⚠️ **不能**直接 `{DynamicResource}` | 见下方「坑 1」 |
| `MainWindow.xaml:219-221` LoopModeCombo 的 `ComboBoxItem.Content` | `{DynamicResource}` | ComboBoxItem 是 ContentControl，DP 上支持 |
| `SettingsWindow.xaml` Tab 头 / 标签 / 按钮 / CheckBox Content | `{DynamicResource}` | |
| `SettingsWindow.xaml:80-86 / 101-107 / 178-186` 内联 `<Run>` 强调段 | 段落级 key + `{DynamicResource}` | Run 是 `FrameworkContentElement`，理论上支持动态资源，**但需实测**；不行就退化为段落级纯文本 + 单独一行强调 |

**第 2 档 · 代码构筑的 UI（41 条）** —— 用 `SetResourceReference`，它们也能热切换

`AboutDialog.cs` / `ExportDialog.cs` / `PromptDialog.cs` 全在 C# 里 new 控件。现在写的是：

```csharp
root.Children.Add(new TextBlock { Text = "版本 " + AppPaths.AppVersion, … });
```

改成：

```csharp
var tb = new TextBlock { Foreground = em, Margin = new Thickness(0, 4, 0, 0) };
tb.SetResourceReference(TextBlock.TextProperty, LocKeys.About.Version);  // 动态绑定
root.Children.Add(tb);
```

带插值的（`$"内嵌曲目 {n} 首 / {m} 部作品"`）不能纯资源，见第 3 档。

**第 3 档 · 算出来的文本 —— 这才是真成本**

这些是"读一次数据 + 拼一句自然语言"，语言变了必须**重跑生成它的那个方法**。好消息是：**这些刷新方法绝大多数今天就已经存在**（因为切曲、换列表时本来就要刷），热切换主要是"把它们集中调一遍"。

| 文本 | 生成处 | 现有刷新入口 |
|---|---|---|
| 播放列表摘要 `{n} 首` | `MainWindow.xaml.cs:321/326/338` | `UpdatePlaylistSummary` 一类 |
| 正在播放区标题 / 详情 | `MainWindow.xaml.cs:422/1145-1148/1155-1165` | `RefreshNowPlaying()` ✅ 已有 |
| 副版 / 灵界版按钮 Content | `MainWindow.xaml.cs:1246/1252` | `RefreshVariantControls()` ✅ 已有 |
| 播放按钮 `▶ 播放` / `⏸ 暂停` | `MainWindow.xaml.cs:1336` | 播放状态回调 ✅ 已有 |
| 收藏按钮 `♥ 收藏` / `♡ 收藏` | `MainWindow.xaml.cs:742/747` | `UpdateFavoriteButton` 一类 |
| 窗口标题 / 不可写警告 | `MainWindow.xaml.cs:1546/1549` | 启动期一次性，抽成方法即可 |
| 右键菜单项（每次打开时新建） | `MainWindow.xaml.cs:764-813` | **天然免疫**：`ContextMenuOpening` 时现建，下次打开自动是新语言 |
| 设置页校验状态（34 条的来源） | `PathValidator` → `SettingsWindow.xaml.cs:85` | 需在语言变更时重跑 `Revalidate()` |
| 导出进度 / 导出完成 | `ExportDialog.cs:267/292/297` | 进度回调，重绘即可 |
| 关于对话框的动态行 | `AboutDialog.cs:241/250/259` | 对话框每次新开，**天然免疫** |

**结论**：需要在语言变更时显式重跑的，是**主窗口与设置窗口当前可见的那些文本**。建议定义一个极小的接口：

```csharp
internal interface IRelocalizable { void OnLanguageChanged(); }
```

`MainWindow` 与 `SettingsWindow` 实现它，语言切换时遍历 `Application.Current.Windows` 调一遍。合计约 6 个方法，都是已有逻辑的重新调用 —— **不需要新的业务代码**。

**坑 1 · DataGrid 列头不能依赖 DynamicResource**

`DataGridColumn` 不是 `FrameworkElement`（它只继承到 `DependencyObject`），不参与可视化树，DynamicResource 找不到资源宿主，解析会静默失败 —— 表现是**列头空白**，且不报错。本项目 `MainWindow.xaml:156-160` 正好有 5 个列头。

可靠做法：列头文本在 `OnLanguageChanged()` 里显式赋值。

```csharp
GameColumn.Header = Loc.S(LocKeys.Grid.Game);
NoColumn.Header   = Loc.S(LocKeys.Grid.No);
…
```

**坑 2 · 字体默认链的"跟不跟"判断**

`UiSettings.DefaultFontChain`（`AppSettings.cs:64`）现在是 `"Yu Gothic UI, Meiryo UI, Microsoft YaHei UI"`。既然要热切换，就得决定：用户切到日语时，界面字体要不要跟着换成日语优先的链？

难点在于 `FontFamily` 一旦写进 settings.json 就是显式值，分不清"用户自己选的"还是"上次自动填的默认"。建议做法：**默认情况下字体链存空串（表示"用语言对应的默认"）**，用户手选后才落具体值。这样热切换时字体自然跟随，用户手动改过的又不会被覆盖。这与 §6.5 是同一件事，只是热切换把它从"可选优化"变成"必须处理"。

**坑 3 · 切换的原子性**

`Application.Current.Resources.MergedDictionaries` 的替换与 `OnLanguageChanged()` 的重跑之间，如果有一次布局/渲染穿插进来，会看到一瞬间的混排。建议在同一帧内完成：替换字典 → 遍历窗口重跑 → `Save()` 落盘。不要中途 `await`。

**两条安全网，别跳过：**

- **阶段 1 是"重构"与"翻译"的分界线**。它做完时只有一种语言，所以任何界面变化都一定是重构 bug，与语言无关，当场能抓。如果阶段 1 和 4 混着做，出了问题分不清是抽错了还是翻错了。
- **阶段 2 的验收要"双语言对切"**：因为热切换最常见的 bug 不是"没翻译"，而是"漏刷"—— 某个按钮还留着上一次语言的文字。只验证从启动就在日语，是抓不到漏刷的。

## 6. 已知的坑

### 6.1 固定像素宽度会被日语撑破

XAML 里大量按中文长度调的固定值：

| 位置 | 现值 | 风险 |
|---|---|---|
| `MainWindow.xaml:215` `LoopModeCombo` | `Width="96"` | 「无限循环」→「無限ループ」多一个假名字，含下拉箭头后余量见底 |
| `MainWindow.xaml:10` 窗口 `MinWidth` | 860 | 列头「作品/曲序/曲名/时长/循环」→「作品/曲番/曲名/長さ/ループ」 |
| `MainWindow.xaml:156-160` 列宽 | 72 / 56 / \* / 86 / 150 | 「循环」列内容含 `intro … · loop …`，日语化后要复核 |
| `SettingsWindow.xaml:111,190` 标签列 | `Width="150"` | 「切曲淡音（秒）」→「曲切替フェード（秒）」≈ 1.4× |
| `SettingsWindow.xaml:37` 校验状态列 | `Width="190"` | 状态文案本来就长（"1 个容器 · TFPK · 首包 12 MB"） |

**好消息**：ja 与 zh 同属 CJK，技术词多用汉字（「循环次数」→「ループ回数」只差一个假名），膨胀率约 1.1–1.4×，远低于英文的 1.8–2.2×。所以这是**复核项**而不是**重设计项**。设置页三大段说明文有 `ScrollViewer`，变长只是变高，安全。

### 6.2 设置页的内联 `<Run>` 强调段

`SettingsWindow.xaml:80-86 / 101-107 / 178-186` 是把一段话拆成多个 `<Run>`、其中若干带 `Emphasis` 画刷。这类文本不能整段塞进一个 key。

**建议**：拆成"段落级 key + 分片 key"，例如 `path.intro.p1` / `path.intro.p2` / `path.intro.p3`，每个 key 内可用 `{0}` `{1}` 占位强调片段由 XAML 侧拼。**不要**往资源值里写 XAML 标记——那会让翻译者面对标签，也会让未来的 Web/CLI 复用不可能。

> 选热切换后这里还有一条额外要求：`<Run>` 上的文本也必须走 `{DynamicResource}`。`Run` 继承自 `FrameworkContentElement`，理论上支持动态资源，但它在 WPF 里属于比较边缘的路径，**实现时必须实测**（切一次语言看这段说明文有没有变）。实测不通就退化为"整段纯文本用 DynamicResource + 强调单独成行"。

### 6.3 加速键

`MainWindow.xaml:39/46/53` 的 `设置(_S)` / `播放列表(_L)` / `帮助(_H)`。日语版要重新挑字母并检查不与子项冲突。日语 UI 传统上用得少，也可以整体去掉 `_`。这是翻译时的人工决策，不是自动化能解决的。

### 6.4 漏键不报错

无论选 resx 还是 JSON，**缺一个 key 都不会编译失败**，运行时表现为空白或 key 原文。必须有 `tools/check_loc.py`：

1. ja.json 与 zh-Hans.json 的 key 集合完全一致；
2. json 里所有 `{0}`/`{1}` 占位符在两种语言下数量一致；
3. 源码/XAML 里引用到的所有 key 都存在于默认 json。

这三条能挡掉 90% 的低级事故。

### 6.5 字体默认链要按语言给

`UiSettings.DefaultFontChain`（`AppSettings.cs:64`）现在是 `"Yu Gothic UI, Meiryo UI, Microsoft YaHei UI"` —— 日文优先。设成日语界面时这是对的；但用户选了简体中文时，`Microsoft YaHei UI` 排最后其实也能命中（前两个在中文 Windows 上多数也存在）。

选热切换后这件事从"可选优化"变成"必须处理"，因为用户会在两个语言之间来回切，字体不跟随会很突兀。方案与难点见 **§4.6 坑 2**（核心是让默认值可表达为"空"，从而区分"用默认"和"用户手选过"）。

### 6.6 切换后仍留在旧语言的角落

热切换最容易漏的不是"没翻译"，是"漏刷"。已识别的高风险点：

| 位置 | 为什么容易漏 |
|---|---|
| `DataGrid` 5 个列头 | DynamicResource 会静默失败（§4.6 坑 1），必须显式赋值 |
| 已打开着的设置窗口的校验状态 | 那是 `Revalidate()` 的产物，不是绑定 |
| 窗口标题 | `MainWindow.xaml.cs:1546` 是代码赋的，不是 XAML |
| 「程序目录不可写」警告 | `MainWindow.xaml.cs:1549` 同上 |
| 正在播放区的详情前缀（「霊界版 · …」） | `RefreshNowPlaying()` 拼的 |
| 已打开的 ExportDialog 进度行 | 进度回调只在导出进行中跑 |

建议做一张**切换后逐项打勾的验收表**，而不是"看起来都变了"就算过。

### 6.7 其它零碎

- `ThbgmPlayer.csproj:30` `<Product>东方 Project BGM 播放器</Product>` —— exe 属性里的产品名，编译期固定，不进资源。可接受，也可以顺手改成中性名。
- `AboutDialog.cs:259` 的 `"运行时 .NET Desktop Runtime {ver}（含 WPF / Windows Forms※）"` 是动态串，注意占位符位置在两种语言下可能不同。
- `MainWindow.xaml.cs:1145-1148` `Describe()` 拼的 `"{rate}Hz / {ch}ch / {bit}bit · intro … · loop … · 总长 …"` 是技术信息 + 一个中文标签的混合体，拆分时要小心别把 `intro`/`loop` 这种术语也翻了。
- `Theme.Get(key, fallbackHex)` 的机制（`UI/Theme.cs:18`）是"从应用资源取画刷"，将来"从应用资源取文案"可以复刻同一模式，三个代码对话框不必各写一份查找。

## 8. 曲名简中化与 UI 本地化的解耦边界

> 2026-09-19 追加。用户另开一线在做曲目的「日语名 ↔ 简体中文名」整理，问这条线能否与本文的 UI 本地化解耦。
> 结论：**可以完全解耦，而且接入点已经是对的** —— 但有一个会静默出错的编号陷阱必须先钉住。

### 8.1 结论：键已经天然对齐，实测零错位

判据是：另一线的数据键，是否等于播放器的身份键 `TrackRef(GameId, TrackDef.No)`（`TrackRef.cs:7`，序列化为 `"th13:16"`，也是 favorites.json / playlists.json 里落盘的形态）。

实测（`musiccmt.json` ↔ `tracks.json.gz` / `tracks.nc.json.gz`，键 → 归一化后的**日文曲名**逐条比对）：

| 范围 | 作品数 | 键数 | 同名 | 错位 | 缺号 |
|---|---:|---:|---:|---:|---:|
| th06 / th07 / th08 / th09 / th095 / th10 / th11 / th12 / th125 / th128 / th13 / th14 / th143 / th15 / th16 / th165 / th17 / th18 / th185 / th19 / th20 | 21 | 329 | **329** | **0** | 0 |
| th06nc（新典） | 1 | 18 | **18** | **0** | 0 |

**含 th07/th08 那两处「物理顺序 ≠ 音乐室顺序」的错位段，也是全部对上。** 所以中文曲名**不需要任何映射表或重编号**，`title_zh` 可以直接挂到 `TrackDef.No` 上。

另一条有利事实：**副版（th13 霊界版 13 首 / 新典原编曲）不引入新的身份键。** 它是 `TrackDef.Alt` 的嵌套子节点（`TrackIndex.cs:53`），不单独成条目，且播放器本来就规定「副版曲名沿主版、只在按钮和详情前缀上体现状态」（`MainWindow.xaml.cs:1136`）。**所以中文名只需覆盖主版，副版不用管。**

### 8.2 曲序项目里有明文规定，实现完全符合 —— 出问题的是 md

**规定**（`design/DESIGN_v3.md` §4.2）：

> **列表顺序：按音乐室编号（`musicNo`）升序。**
> 无编号曲目**补号**（接该作最大编号往后加，排在该作末尾），共 13 条。

**实现核对**（实测 `tracks.json.gz` / `tracks.nc.json.gz`）：

| 检查项 | 结果 |
|---|---|
| 各作 `n` 是否 1..N 连续无缺口 | 21 作**全部连续** ✓ |
| §4.2 列出的 13 条补号 | 逐条对上，**13 / 13** ✓ |
| 可见曲数 | 333，与 §4.2 表述一致 ✓ |
| 副版不单列 | th13 的 13 首灵界版挂在 `alt` 子节点，不占 `n` ✓ |

**结论：曲序是既定项，不是待定项。** 播放器 `TrackDef.No` ＝ §4.2 的曲序；`musiccmt.json` 的键也用它。**三者一致，且是设计使然，不是巧合。**

**真正错位的是 md**：`docs/musiccmt/*.md` 的 `##` 段号用的是 `tracklist.csv` 的 **`index`（物理序 = 音频文件名序）**，而不是 `musicNo`。th07 与 th08 末尾各 6 首因此与播放器序错位，共 **12 首**。以 th07 为例：

| 曲名 | 文件名 | 播放器 No ＝ musiccmt 键 | md 段号（物理序） |
|---|---|---:|---:|
| 春風の夢 | th07_14.wav | 19 | 15 |
| さくらさくら ～ Japanize Dream... | th07_15.wav | 20 | 16 |
| 妖々跋扈 | th07_16.wav | 15 | 17 |
| 少女幻葬 ～ Necro-Fantasy | th07_17.wav | 16 | 18 |
| 妖々跋扈 ～ Who done it! | th07_18.wav | 17 | 19 |
| ネクロファンタジア | th07_19.wav | 18 | 20 |

> `docs/musiccmt/README.md` 自己写的是「每作一个 md，**按播放器曲目顺序**列出」，但实际是物理序。所以是 **md 没有遵守它声明的规则**，而不是规则缺失。
> 处理方式二选一，都不影响 `musiccmt.json`（它本来就是对的那一个）：
> **(a)** 改 README 那一句，承认 md 按物理序（成本最低，且保留了"与源文件逐行可比对"的好处）；
> **(b)** 把 md 的段序重排为曲序（th07/th08 各挪 6 段；段标题括号里的「音乐室 #N」已在，改造成本可控）。
> 属用户资产，未擅改。

**误用 md 段号当键的后果**：12 首中文名串位，且**肉眼几乎发现不了** —— 每一条配对都是同一部作品里的真实曲名，日文名合理、中文名也合理，只是彼此不对应。唯一能抓出来的是校验 **ja↔zh 配对本身**，而不是看单边像不像。

**因此规则只有一条：以 `musiccmt.json` 为唯一真源，不要从 md 提取。** 若必须从 md 工作，键取段标题括号里的「音乐室 #N」，**不是** `##` 后面的段号。

**另外不要用曲名当键**：同一首曲在不同来源表记不同 —— th07 #17 omake 作 `Who done it?`、音乐室作 `Who done it!`；th08 #8 omake 句尾有句点、音乐室没有（见 `docs/musiccmt/README.md`）。

> **⚠ 顺带发现：§4.2 的「`musicNo` 原值仍保留在索引里」没有实现。**
> §4.1 的字段表与 §4.2 都说补号后 `musicNo` 原值（null）仍保留在索引里，但实测 `tracks.json.gz` 里**根本没有 `musicNo` 字段** —— 全部出现过的字段名只有 `alt, b, c, f, i, l, n, r, s, t`。
> 后果：**补号做了，原值没留**。所以从索引无法区分「真音乐室号 18」与「补号 18」（例：th11 的 No=18 プレイヤーズスコア 是补号，而 th07 的 No=18 ネクロファンタジア 是真音乐室号）。
> 对播放器功能无影响，也不影响本条线的键对齐；但属于**文档与实现的漂移**，将来若要用 `musicNo` 做任何事（从游戏文件反查、重新生成 CSV、按音乐室号筛选）会踩到。要么补字段，要么改 §4.1/§4.2 的表述。

### 8.3 三条需要现在钉住的接缝

| # | 接缝 | 现状 | 建议 |
|---|---|---|---|
| 1 | **身份键** | 两侧已对齐 | 统一 `gameId + music_no`。禁用 md 段号；禁用文件名（`th07_14.wav` 是 index 15）；禁用曲名字符串 |
| 2 | **显示规则** | 未定，且与既有规格冲突 | 见下 |
| 3 | **载体** | 未定 | 中文名是**内容数据**，走索引（或 `tracks.override.json`），**不要塞进 `lang/`** |

**接缝 2 是唯一真正的耦合点，必须连同规格一起改口径。** 现状有三处互相咬合：

- `design/DESIGN_v3.md` §1.4 硬约束：**「曲名一律日语原名，不显示译名」** —— 若中文界面要显示中文曲名，这条硬约束必须改写。
- `Core/AppSettings.cs:77-81` `ContentFontFamily`，注释写的是「**日文内容**：曲目表、正在播放区、导出清单里的曲名与作品名」—— 曲名一旦可能是中文，这条设置的语义要重新表述（"曲名字体"还是"日文曲名字体"）。
- `MainWindow.xaml:158` 曲名列 `Width="*" MinWidth="240"` —— 中文名与日文名长度不同，需要复核。

**接缝 3**：把 581 条曲名塞进 `lang/` 会让 UI 资源表膨胀一个数量级，并让"每加一门语言就得多翻 581 条曲名"成为强制项。曲名是内容，`lang/` 只装界面外壳（§2.1 已划）。`tracks.override.json` 是 DESIGN_v3 §2 预留的机制，但它今天的语义是**用户手改覆盖**，不是第二语言资源 —— 要明确它承担哪个角色，或另开一个 `titles.<culture>.json`。

## 9. 切换范围的核定

> 2026-09-19 追加。用户提出的切换范围是：**UI 界面 / 播放列表 / 乐评区 / 曲目信息显示**（后者"应该也可以走切换，只是资料不全"）。
> 核定结论：**方向对，但要拆成两类；有 1 项定性要改、1 项要拆开、1 项漏了。**

### 9.1 总纲：一次切换动作，两条数据通路

| | 外壳多语言 | 内容多语言 |
|---|---|---|
| **范围** | UI 界面文案、播放列表的界面文案 | 曲名、乐评、作品名 |
| **载体** | `lang/*.json`（内嵌 + 目录覆盖） | 数据层：`tracks*.json.gz` / `musiccmt.json` |
| **定位键** | key 字符串（`main.menu.settings`） | `gameId + musicNo` |
| **"切换"的含义** | **替换文本** | **换一个字段取值**（同一对象，取另一语言的那一栏） |
| **规模** | 约 170 条，全部是短句 | 曲名 581 条；乐评正文 ja 约 3.8 万 / zh 约 3.2 万字 |
| **实现阶段** | §4 主体 | §8 已覆盖曲名，乐评见 §9.4 |

**这条分界不是学究，它有硬后果**：内容若进 `lang/`，会同时带来两个问题 ——
① 资源表膨胀一个数量级（乐评是长文）；② **每加一门语言就变成强制要翻 581 条曲名 + 7 万字乐评**。而乐评正文的现实名源只有 thpatch 的 ja / zh-Hans 两份，第三门语言大概率永远不会有。一旦某个语言的 `lang/` 是"半成品"，`lang/` 就不再能表达"这门语言可用"这个语义了。

**两条通路必须挂在同一个动作上。** 所以 §4.2 的 `IRelocalizable.OnLanguageChanged()` 职责要加一条：不只是"重算算出来的文本"，还要"**重取内容字段**"。这是对 §4.6 的补充。

> ⚠ 本节末尾由 **§10** 修订：用户已决定给两条通路**各设一个入口**（界面语言 / 内容语言），
> 因此"同一个动作"只在**内容语言 = `auto`** 时才成立。详见 §10.1。

### 9.2 逐项核定

| 用户列出的项 | 归类 | 结论 |
|---|---|---|
| UI 界面 | 外壳 | ✓ 无异议（§3–§7 的主体） |
| 播放列表 | **要拆成三份** | 只有"界面文案"那份该切，见 §9.3 |
| 乐评区 | 内容 + **新功能** | 定性要改：它不是本地化项，见 §9.4 |
| 曲目信息显示 | 内容 | "资料不全"不该是阻塞项，关键在回退策略，见 §9.5 |
| **作品名** | 内容 | **你这四项里漏了**，见 §9.6 |

### 9.3 播放列表：要拆成三份，只有一份该切

| 份 | 例子 | 代码位置 | 切不切 |
|---|---|---|---|
| 界面文案 | 「添加到列表」「＋ 新建列表…」「收藏」「★ 收藏」 | `MainWindow.xaml.cs:764-813`、`:263` | **切**（外壳） |
| 自动生成的默认名 | 「我的列表 1」「列表 2」 | `MainWindow.xaml.cs:1462`、`PlaylistStore.cs:63` | **生成时按当时语言**，落盘后不回溯 |
| 用户自己起的名字 | 「我最爱的 10 首」 | 用户输入 | **永远不切** |

后两份会落盘到 `playlists.json`。**用户起的名字是他的数据，不是我们的文案** —— 切一次语言就把人家的列表改名，是数据损坏级别的错误。这一条要写进规格，否则实现时很容易顺手全刷。同理，已生成的默认名也不回溯（否则同一份 json 会随语言漂移，失去可预期性）。

### 9.4 乐评区：不是本地化项，是一个从零开始的新功能

**核查结果**：`design/DESIGN_v3.md` 全文**没有**任何"评论 / 乐评 / comment"字样；`src/` 下**也没有**任何评论相关代码。当前主窗口的六行布局（菜单 / 播放列表选择 / 曲目表 / 进度条 / 播放控件 / 当前曲目信息）里没有它的位置。

所以乐评区是**新功能**，本地化只是它的一部分。实际影响：**乐评区的排版与交互设计**（放哪、怎么滚、要不要折叠、要不要跟选中的曲目联动、长文用什么字体）是独立的一件事，可以并行推进，但**不要在定乐评区 UI 的时候顺手把本地化机制也定死** —— 反过来也一样，本地化方案不该预设乐评区长什么样。

**资料成色：比曲名齐得多。** 实测 `docs/musiccmt/musiccmt.json`：

| 项 | 覆盖 | 备注 |
|---|---|---|
| 曲目条目 | 347 条（21 作 + 新典） | |
| `comment_ja` | **338 / 347** | |
| `comment_zh` | **338 / 347** | **与 ja 完全同步，无一条单边缺失** |
| 裏音楽コメント `ja` / `zh` | 各 **58**（th06 17 + th07 20 + th08 21） | 也是 ja/zh 同步 |
| 正文规模 | ja 约 **3.8 万字** / zh 约 **3.2 万字** | 内存驻留毫无压力（整个 json 275 KB） |

缺的 9 条（`comment` 那两列的 347−338）**不是"没整理"，是原游戏本来就没有评论**：th11–th18 各 No=18 `プレイヤーズスコア`、th125 No=7 `はたてアンロック`。**日文与简体中文之间没有任何一边有一边没有的洞** —— 这是很干净的成色，比曲名那 234 条缺口好得多。

### 9.5 曲目信息显示：可以做，关键是先定回退策略

## 10. 双入口方案核定（界面语言 / 内容语言）

> 2026-09-19 追加。用户提出：**UI 多语言走常规方案；涉及播放内容的（游戏标题、曲目标题、乐评内容）另设一个入口切换。**
> 核定结论：**采纳**。这比单一开关更好，但必须补一条默认值规则，并把几个"骑墙"项当场归位。

### 10.1 为什么比单一开关好

**核心论据：两个语言列表的长度天然不同。**

界面语言可以加第三、第四门（比如英语），但内容侧的资料是手工做的 —— 曲名 347/581、乐评只有 thpatch 的 ja / zh-Hans 两个来源、作品名零名源（§8.4 / §9.4 / §9.6）。所以"界面有 N 门语言、内容只有 2 门"是**常态而非例外**。

| | 单一开关 | 双入口 |
|---|---|---|
| 用户选了没有内容资料的语言（如英语） | 界面英语 + 内容被迫回退 → **界面上出现"半英语半中日"且没有任何文案能解释原因** | 英语只出现在「界面语言」列表里，根本不进「内容语言」列表 → 用户不会产生疑问 |
| 加一门界面语言 | 立刻暴露"内容侧没有这门语言" | 界面侧独立演进，内容侧不受影响 |
| 内容的回退策略归属 | 与界面回退混在一起 | 干净的"内容语言 X 缺这条 → 退回 ja" |

另有两个附带收益：

1. **消解了 §9.1 的"同帧完成"约束。** 双入口下：改界面语言（内容语言为显式值）→ 只换资源字典，内容不动；改内容语言 → 只重取字段，字典不动。**两种情况下都不存在半帧混排。** 唯一仍需两条通路同帧的情形是「内容语言 = `auto` 且改的是界面语言」——约束从"永远"缩小到"auto 模式下"，实现明显简化。
2. **回退策略的复杂度被隔离。** §9.5 的逐曲/整作回退，现在只影响"内容语言"这一侧，不用去动界面语言的加载逻辑。

### 10.2 必须补的一条：内容语言默认 `auto`（跟随界面语言）

若两个开关完全独立、没有联动，用户切了界面语言却发现曲名没变，**会当成 bug**。所以内容语言的取值必须是三态：

```jsonc
"content": { "language": "auto" }   // auto | ja | zh-Hans
```

`auto` = 跟随界面语言。**绝大多数用户永远不会去碰第二个开关。**

> 这是 §4.6 坑 2（字体链）同款问题的标准解法：**把"跟随"表达成一个可存储的取值**，而不是靠"当前值 == 默认值"来猜用户有没有手选过。字体链那边是"空串 = 跟随"，这边是 `auto`。

### 10.3 骑墙项的归置（必须现在定，否则实现时会各写各的）

| 项 | 位置 | 归属 | 理由 |
|---|---|---|---|
| 副版按钮「霊界版 / 新典 / 原典」 | `GameDef.MainLabel` / `AltLabel`（`TrackIndex.cs:116-117`） | **内容语言** | 它是**索引里的作品元数据**，与曲名同源。虽然渲染在按钮上，但归属看来源不看控件 |
| `TrackRow.LoopText` 的「不循环」 | `MainWindow.xaml.cs:26` | **界面语言** | 是 UI 用语，不是数据 |
| `Describe()` 的技术串 | `MainWindow.xaml.cs:1145-1148` | **混合串，要拆** | `{rate}Hz / {ch}ch / {bit}bit · intro … · loop …` 是中性的技术信息（不切或只切单位）；句尾「总长」才是外壳文案，拆出来走界面语言 |
| `TrackRow.DisplayText` 的拼接 | `MainWindow.xaml.cs:57` | 分隔符属界面，两个名字属内容 | `"{作品名} - {曲序} - {曲名}"` |
| 「作品」列的 `GameCode`（TH06…） | `MainWindow.xaml:156` | **两边都不切** | 中性代号 |
| 导出文件名 | `WavExporter.cs:38` | **两边都不切** | 见 §2.3：数据产物，要可预期、可被脚本消费 |
| 用户自起的播放列表名 / 已落盘的默认名 | `playlists.json` | **两边都不切** | 见 §9.3 |

### 10.4 配置结构与落位

**配置**建议新开一类，而不是塞进 `UiSettings`：

```jsonc
{
  "ui":      { "language": "ja" },        // 界面语言
  "content": { "language": "auto" }       // 内容语言：auto | ja | zh-Hans
}
```

理由：内容侧将来还会有别的设置 —— 比如乐评区要开关"是否显示裏音楽コメント""是否显示原编曲版评论"（§9.4）。塞进 `UiSettings` 名不副实。`AppSettings.Version` 不用动（加字段向后兼容）。

**落位**：建议新增一个**「语言」Tab**，里面就两行 ——「界面语言」「内容语言」。
比拆开放进「外观」页好，因为这两项**必须并排**用户才能理解它们的区别；但也不该和字体、主题混在一起（它们不是外观）。

> 这条替换了 §7.2 的遗留项 A（语言选择器落位）。

**内容语言列表固定列出 ja / zh-Hans 两门，不随资料可用性增减。** 若让列表跟着资料走，设置项会随资料补进度增删，用户无法预期；资料缺失交给 §9.5 的回退策略处理。

### 10.5 这个方案消解/改变了哪些前面的结论

| 前文 | 变化 |
|---|---|
| §9.1「两条通路必须挂在同一个动作上、同帧完成」 | **部分消解**：仅在 `auto` 模式下成立（§10.1） |
| §4.2 的 `IRelocalizable.OnLanguageChanged()` | 职责不变，但**触发源变成两个**：界面语言变更 → 外壳部分重刷；内容语言变更（或 auto 联动）→ 内容部分重取 |
| §7.2 遗留项 A（语言选择器落位） | 已由 §10.4 给出建议（新增「语言」Tab） |
| §9.5 曲名回退策略 | 归属明确到"内容语言"一侧，不再与界面相关 |

### 10.6 风险与缓解

| 风险 | 缓解 |
|---|---|
| 两个开关，用户分不清区别 | ① 内容语言默认 `auto`，多数用户不碰；② 设置页写一行说明："内容语言默认为跟随界面语言；改这里只影响曲名、作品名与乐评" |
| 组合测试面 | 2 × 2 = 4 种组合 + `auto`，可控。验收时四种都过一遍即可 |
| 实现时两条通路各写一套刷新逻辑 | 用同一个 `IRelocalizable` 接口，只是分两个触发源（§10.5） |

## 附：一句话备忘

> 本地化的工程量不看"有多少字符串"，看"有多少地方在**生产**字符串"。
> 这个项目里，前者是 248，后者是 5 个层。**先把生产者收到 1 个，再谈翻译。**
>
> 而热切换的工程量不看"有多少个 Text"，看"有多少文本是**算出来的**" —— 那批文本需要在语言变更时被**重算一次**，
> 而不是被"翻译一次"。§4.6 第 3 档就是这份名单。
>
> 切换入口的工程量不看"有几个开关"，看"有几处文本的**归属是模糊的**" ——
> 副版标签、`Describe()` 混合串、导出文件名就属于这一类，§10.3 是这份名单。
