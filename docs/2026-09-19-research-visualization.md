# 音频可视化 / 波形显示 — 前期调研

日期：2026-09-19 · 状态：调研完成，未定规格，未动代码

## 结论

支持。现有播放管线是纯托管的 `ISampleProvider` 链，采样数据在进 WASAPI 之前全部以
float 44100Hz/2ch 形式流过应用层，可视化需要的两种数据（实时采样流、整轨 PCM）
都能在不改动播放内核的前提下拿到。**不需要引入任何新依赖**（FFT 用 NAudio 自带的
`NAudio.Dsp.FastFourierTransform`，渲染用 WPF 内置手段即可）。

## 一、现有管线与取数点

```
IAudioSource(源采样率) → LoopSampleProvider → [WdlResampling 22050→44100]
    → CrossfadeMixer → VolumeSampleProvider → SampleToWaveProvider16 → WASAPI 共享模式
```

关键事实（源码核实）：

- `CrossfadeMixer.Read` 输出恒定 float 44100/2ch，且**始终返回满长度**（静音也读）。
  取数点放在混音器之后，所有源（thbgm.dat / TH06 wav / 灵界版 22050 / 黄昏 OGG /
  新典 Opus）都被归一成同一种格式，可视化层无需关心来源差异。
- 取数点放在混音器之后还能天然覆盖交叉淡化过程（切曲 / 灵界版切换的淡化段会如实显示）。
- 取数位置二选一，语义不同：
  - **混音器后、音量前**：可视化不随音量条变化（推荐，音量关小画面不衰减）；
  - **音量后**：可视化跟随音量（所见即所听）。
- 输出延迟 100ms：取到的采样比实际出声的早 ~100ms，对频谱条 / 示波器无感。

## 二、两条路线

### 路线 A：实时可视化（频谱条 / 示波器 / 电平表）

数据通路：在链上插一个「分接」`ISampleProvider`（透传 Read，同时把样本拷进
预分配的环形缓冲），UI 线程按 30–60fps 取数渲染。

- **FFT**：`NAudio.Dsp.FastFourierTransform`（NAudio 3.0.1 内置，复数 FFT，
  长度取 2 的幂，1024/2048 窗口足够）。零新依赖。
- **成本估算**：44.1k×2 float/s ≈ 350KB/s 的环形拷贝，可忽略；
  2048 点 FFT 每帧一次 < 0.1ms。
- **渲染方案对比**：

  | 方案 | 开销 | 适合 | 备注 |
  |---|---|---|---|
  | Canvas + Polyline/Path | 中（每帧分配几何） | 简单示波器 | 60fps 下 GC 有压力，够用但不优雅 |
  | DrawingVisual + RenderOpen | 低 | 频谱条、示波器 | **推荐**，免分配、纯 retained-mode |
  | WriteableBitmap | 低 | 频谱图（spectrogram 瀑布） | 逐像素，经典做法 |
  | SkiaSharp.Wpf | 最低（GPU） | 高帧率复杂效果 | 引入新依赖，与本项目「依赖白名单、纯托管、便携」取向冲突，不建议 |

- **线程纪律**（重点）：取数回调跑在 MMCSS "Pro Audio" 线程上（PlayerEngine 已设置），
  分接器里**禁止分配、禁止锁竞争**——环形缓冲预分配 + 无锁单写单读即可。
- **暂停语义**：暂停时管线不再被读，环形缓冲里的数据会停在原地。
  需要决定「冻结」还是「衰减归零」（衰减更自然，实现是 UI 侧乘衰减系数，不动音频线程）。
- **灵界版切换 / seek / 切模式**：因为取数点在混音器后，这些操作引起的
  Reconfigure / SwitchAlt 对可视化完全透明，不用额外处理。

### 路线 B：整轨波形总览（SoundCloud 式静态波形 + 循环区高亮 + 进度标记）

这个方向和本项目的循环特性契合度极高：`IAudioSource` 直接暴露
`IntroBytes` / `TotalBytes`，循环区在波形上能**精确对齐**标注。

- 数据来源：音源不是全量驻留内存的，是 seek+read 流式读。
  需要**后台线程把整个音轨扫一遍**（顺序 Read，按块算 min/max 峰值，
  例如每 2000 帧出一个峰对），扫完释放。
- 成本：一首 3 分钟的曲子 ≈ 32MB PCM（44100/16bit/2ch），解码一遍的 CPU
  开销 OGG/Opus 约 1–3 秒、裸 PCM 读盘毫秒级。做成「首次点播某曲时后台生成，
  生成前区域显示占位」即可。
- 缓存：禁止写 APPDATA → 峰值数据要么**只存内存**（每曲几 KB：3min/2000帧 ≈ 2646 峰对
  × 8B ≈ 21KB，整个播放列表也才几 MB，推荐），要么落 bgmplayer/ 下的缓存文件（可持久）。
- 可以和进度条结合：波形上叠 loop 段高亮、当前进度游标，点击波形 seek
  （`Seek` / `SeekLoop` 都是现成的）。

## 三、UI 落位

主窗口是 6 行 Grid（菜单 / 播放列表 / 曲目表★ / 进度条 / 播放控件 / 当前曲目）：

- 方案 1：在「进度条」行上方或下方加一行固定高度（90–140px）的可视化条带，
  对现有布局零侵入，窗口 MinHeight 600 仍可容纳。
- 方案 2：与「当前曲目信息」行合并为右侧波形 + 左侧文字的两列布局。
- 建议做成**可在设置里开关**（默认开），关闭时行高收为 0，不影响现有用户。
- 主题：DarkTheme.xaml 的 BgPanel / Border / Accent 画刷直接可用，视觉风格一致。

## 四、约束核对

| 约束 | 影响 |
|---|---|
| 禁写 APPDATA | ✅ 峰值缓存走内存，或 bgmplayer/ 目录 |
| 依赖白名单 / 纯托管 / 便携 | ✅ FFT 用 NAudio 内置；渲染用 WPF 内置，不引 SkiaSharp |
| tsa/ tf/ tools/ 只读 | ✅ 新增代码全在 src/Audio 与 src/UI |
| 播放内核稳定性（loop 点、淡化） | ✅ 分接器是纯透传节点，不改时序；路线 B 独立开源扫描，不碰播放中的源 |
| Kaspersky | 无特殊影响（无新原生 DLL） |

## 五、风险与待定项

1. 分接器的音频线程零分配纪律（最容易踩的坑，写法需评审）。
2. 暂停时的画面语义（冻结 vs 衰减）——待规格确认。
3. 路线 B 对「正在播放的同一文件」再开一个源做扫描：黄昏 TFPK / dat 都是
   只读打开，并发读无碍，但新典 Opus 解码要扫一遍全轨，需确认后台线程优先级
   不干扰音频线程（线程优先级默认即可，音频线程有 MMCSS 保护）。
4. 可视化内容选型待用户定：频谱条 / 示波器 / 电平 / 静态波形，单选还是组合。

## 六、建议

- **先做路线 B（整轨波形 + loop 区高亮 + 点击 seek）**：信息价值最高
  （直接呼应本项目循环导向的 UI），无实时线程风险，实现量中等。
- **路线 A 后做或并行**：数据现成、接入点干净，但收益偏装饰性；
  若做，渲染选 DrawingVisual，取数点放混音器后、音量前。
- 两条路线共用同一个可视化行区域，上下排布或 Tab 切换均可。

## 七、实时可视化三种方案设计（2026-09-19 追加，已出动态效果稿）

配色遵守 DarkTheme 规矩：中性灰阶 + 单一蓝色强调，不引入第二种彩色。
柱体/描线用蓝系派生色 `#2E86C4`/`#3A96DD`，峰值帽与保持线用 Emphasis `#9CDCFE`，
仅电平表的余量区用语义色 Warn `#CEA86A`（低饱和，表「接近削顶」）。
容器复用条带样式：BgPanel `#222224` + 上下 Border `#3F3F45` + 内嵌 BgDeep `#171717` 画布。

### 方案 A：频谱条（**已定稿** 2026-09-19）

- 取数：2048 点 FFT（NAudio.Dsp），60fps；52 根对数分布频柱（20Hz–20kHz）。
- **对数轴定稿**（用户对比线性轴后拍板；线性版低频压成一团被否）。
- 平滑：attack 0.55 / release 0.12（快攻慢放）；无峰值帽。
- 观感：信息密度最高，和「在播音乐内容」的对应关系最直观；代价是需要 FFT。
- 开销估算：每帧 FFT < 0.1ms + 52 个矩形填充，UI 线程无感。

### 方案 B：立体声示波器

- 取数：无 FFT，环形缓冲直接抽稀（每列 1 代表点，窗口 ~12ms）。
- 绘制：L 蓝 `#3A96DD` / R 浅蓝 `#9CDCFE`（用户 2026-09-19 拍板，由中性灰改，
  同族双蓝以明度区分声道）两条折线叠加 + 中线 `#3F3F45`；线宽加粗（1.6×设备像素）。
- 观感：最「仪表」、最克制，符合本应用气质；但看不出频率构成。
- 开销估算：三者中取数最便宜（纯拷贝），绘制每帧 ~600 点折线 ×2，仍然无感。

### 方案 C：L/R 电平表

- 取数：只对缓冲做 RMS 求和（O(n)，无 FFT 无折线），30fps 足够。
- 绘制：**竖向双条**（用户 2026-09-19 拍板，由初稿横条改竖）、dB 刻度（**-36…0**，
  用户拍板下限由 -50 收到 -36，标注 -36/-24/-18/-12/-6/0）、-6dB 以上余量区 Warn 色、
  条顶 RMS dB 读数（Consolas，呼应进度条字体）；无峰值保持线。
  **J 相位相关表横向挂在竖条电平正下方**（用户 2026-09-19 拍板），量程 -1…+1，
  **全量程统一底色**（用户拍板，负半区 Warn 色撤掉）。
- 观感：功能向（看得出响度与削顶余量），装饰性最低；竖条更接近混音台推子的直觉。
- 开销估算：总开销最低，实现也最简单。

### 共同件

- 分接 ISampleProvider + 预分配环形缓冲（~50ms），三方案共用同一份取数基础设施。
- 渲染循环走 CompositionTarget.Rendering（vsync 驱动，不开定时器）。
- 暂停语义（待定）：缓冲不再更新，画面冻结 or 衰减归零。

## 九、宿主形态评估（2026-09-20 追加，用户提出三案）

用户提出三种窗口/区域形态，问「基于目前的框架是否可行」：

1. **附件窗口**：播放器窗口是本体，可视化像附件一样跟随本体附着显示。
2. **弹出层**：在播放控件之上、播放列表之下的位置弹出。
3. **常驻区域**（后备方案）：直接在主窗口加一块区域。

### 9.1 核心判断：三案共用内核，宿主与内核解耦

这是评估里最重要的一条，它把「三选一」变成了「先选一个、后换得起」：

- 三个方案**共用的东西完全一样** —— 取数分接（`ISampleProvider`）＋ 50ms 环形缓冲 ＋ 四个渲染器
  （A 频谱 / B 示波 / C 电平+J 相关 / D 利萨如），这部分与宿主无关。
- 只有**最后一层「画到哪个 Visual 上」**不同。渲染走 `DrawingVisual`/`DrawingContext`，
  可以画进任意宿主；若改成画进 `WriteableBitmap` 再交给 `Image`，宿主自由度更高（连 DPI 都不用管）。
- 结论：**内核先做一个宿主无关的控件，宿主形态是可后换的实现细节**，换宿主的成本只在「容器搭法」，
  不在可视化本身。所以不需要为这个决定纠结太久。

### 9.2 方案一：附件窗口 —— 可行，但只有一项真成本

**现状支撑（都已存在，不用新建机制）**

| 需求 | 现状 | 出处 |
|---|---|---|
| 第二个窗口的先例 | `SettingsWindow` 就是 XAML 窗口 + 代码 `Owner = this` | `src/UI/SettingsWindow.xaml`、`MainWindow.xaml.cs:1358` |
| 窗口几何持久化 | `UiSettings` 已有 `Width/Height/Left/Top/Maximized`，且带「跑出屏幕则忽略」的校验 | `Core/AppSettings.cs:66-70`、`MainWindow.xaml.cs:166-185` |
| 落盘位置 | `settings.json` 就在 exe 旁，**不写 APPDATA**，满足硬约束 | `Core/AppPaths.cs:22` |
| 多屏工作区计算 | `UseWindowsForms=true`，`System.Windows.Forms.Screen` 可用（需写全称） | `ThbgmPlayer.csproj:10,41-42` |
| P/Invoke 先例 | 已有 `MediaKeysHotkey` 等原生互操作 | `Core/MediaKeysHotkey.cs` |

**`Owner` 免费给到三件事**（很多人误以为要自己写）：

1. 从属窗口恒在属主之上（不会被主窗口盖住）
2. 属主最小化 / 还原时跟着走
3. 属主关闭时一起关闭

**唯一需要自己写的是「位置跟随」** —— `Owner` 不负责位置。主窗口 `LocationChanged` / `SizeChanged`
时按存的偏移量重设附件窗口的 `Left/Top`（拖动过程会高频触发，直接赋值即可，但要防「设位置→触发自身事件」的回环）。

**五个真实坑（按严重度排）**

| # | 坑 | 说明与对策 |
|---|---|---|
| 1 | **`ShutdownMode` 默认是 `OnLastWindowClose`** | `App.xaml` 未覆盖，只设了 `StartupUri`。一旦附件窗口开着而主窗口被关，**进程不会退出**，而 `Window_Closing`（`MainWindow.xaml.cs:1552`）已经把 `_engine` 释放了 → 留下一个「窗口活着但引擎已死」的僵尸态。对策：`App.xaml` 显式设 `ShutdownMode="OnMainWindowClose"`，或在 `Window_Closing` 里显式关掉附件窗口。 |
| 2 | `Owner` 必须在 `Show()` **之前**设 | 之后设会抛异常。 |
| 3 | 最大化 / 全屏时位置语义崩坏 | 主窗口最大化后 `Left/Top` 是最大化位置，「贴在下边」会跑到屏幕外。需要显式定规则（最大化时隐藏、或改贴右侧）。 |
| 4 | DPI / 多屏漂移 | WPF `Left/Top` 是 DIP，跨不同缩放比的显示器会有累计偏差；恢复位置时可直接复用 `MainWindow.xaml.cs:172-182` 那套越界校验。 |
| 5 | Alt+Tab / 任务栏 | `ShowInTaskbar="False"` 只管任务栏；要同时移出 Alt+Tab 需加 `WS_EX_TOOLWINDOW`（`SetWindowLong`），属已有 P/Invoke 风格的活。 |

**明确不做的事**：WPF **没有**内建的窗口吸附 / 停靠。若要「拖过去自动贴边」的体验，得自己写贴边判定与
吸附动画（纯 UX 代码，量最大）。建议先做「恒附着、不可自由浮动」或「自由浮动但不吸附」，
把吸附留作后续增强。

### 9.3 方案二：弹出层 —— 与方案三共用同一行，差别只在「是否占位」

**先纠一个容易混的点**：用户描述的位置（播放控件之上、播放列表之下）**正是进度条所在的那一行**
（`Grid.Row="3"`，`MainWindow.xaml:176`）。所以方案二和方案三插的是**同一个新行**，
真正要分的只是它的行为语义，有两种子变体：

| 子变体 | 行为 | 代价 |
|---|---|---|
| **推挤式** | 展开时新行占位，曲目表被压缩；收起时归零 | 曲目表空间随开合变化（最小窗口下 15 行 → 约 9–11 行） |
| **覆盖式** | 浮在曲目表/进度条之上，不改变任何既有行的高度 | 会遮住底下的内容；需要自己管 z 序 |

**⚠️ 不要用 WPF `Popup` 实现覆盖式**：`Popup` 是独立 HWND，会产生 airspace 问题
（无法被主窗口裁剪、永远浮在所有 WPF 内容之上、渲染走另一条合成通道），
而 `App.xaml:6-11` 那段注释已经说明 Popup 的资源继承是个已知麻烦。
**改用同一个 Grid 里靠后的子元素 + `Panel.ZIndex`** 即可得到同样的视觉，且渲染仍在主窗口的合成通道内。

**改动落点（清单明确）**：在第 2 行与第 3 行之间插一行，然后把 `Grid.Row` 3/4/5 顺移为 4/5/6
（进度条、播放控件、当前曲目信息，共 5 处属性），加一个切换按钮与行高动画。
⚠️ 新行**不能插进 `GridHost` 内部**（`MainWindow.xaml:84-173`，它是框选/排序覆盖层的坐标系）。

### 9.4 方案三：常驻区域 —— 成本最低，空间账见上一节

即早先分析的落法，参数与三种空间代价见「UI 布局基线」记录。它是三案里唯一「零新增窗口基础设施」的。

### 9.5 对比

| | 一 · 附件窗口 | 二 · 弹出层 | 三 · 常驻区域 |
|---|---|---|---|
| 新增窗口 | 是（1 个） | 否 | 否 |
| 主窗口布局改动 | 无 | 插 1 行 + 顺移 3 行 | 插 1 行 + 顺移 3 行 |
| 占用曲目表空间 | 不占 | 收起时不占 | 常占 |
| 可看性 / 沉浸感 | 最高（可放大成全窗） | 中 | 中 |
| 必须自己写的部分 | 位置跟随、可选的贴边吸附 | 弹出动画、z 序 | 无 |
| 已知硬坑 | `ShutdownMode`、最大化语义、DPI、Alt+Tab | `Popup` 的 HWND 陷阱（可规避） | 无 |
| 相对成本 | **高** | 中 | **低** |
| 内核复用度 | 100%（同一控件换宿主） | 100% | 100% |
