## 四、数据通路（`src/Audio/TrackScanner.cs`）

**独立建源 → 顺序读到末尾 → 释放**，照抄两处现成先例：
`WavExporter`（`:76` 建源 / `:101-115` 循环读 / `:121-125` 包 `Task.Run`）与
`PreloadCache`（`:49-68` 后台独立建源、失败静默）。四种解码源构造时已把整轨解进内存。
批量 8192 帧**照抄 `WavExporter:98`**（那条路已跑通所有容器，别自选一个数）。

- ⚠️ **必须独立建源**：播放链上那条源归引擎持有，共用会打断正在播的音频。
- ⚠️ **不许动 `PreloadCache`**：`TryTake` 会把预读源取走、破坏"切曲零等待"。
- 峰值：每 **256 帧**一对 `sbyte` min/max（取 PCM16 的**高 8 位**）。
  ⇒ 量化步长 ≈ 1/128 ⇒ **低于约 −42dBFS 的信号在波形上是平的**（96px 面板可接受；要更细得改存 `short`，内存 ×2）。
- ⚠️ 采样率**随源变**（新典 Opus 是 48k），所以存 `SecondsPerBucket` 而不是假定 44.1k。
- 内存：`桶数 = 总帧/256` × 2B ⇒ 4 分钟立体声 ≈ **82KB/曲**；缓存 `WaveformCache` 纯内存、LRU 64 条。
- 键**直接复用 `PreloadCache.KeyOf`**（它是 public）—— 主/副版是两条音频，必须分开；两份键格式迟早分叉。
- 可取消（`_waveCts` + `_waveGen` 代数丢弃过期结果）。⚠️ 能取消的只是峰值循环读，**整轨解码在 ctor 里取消不了**。

## 五、绘制与算术

- **面板** `src/UI/WaveformPanel.cs : FrameworkElement`（`OnRender` + 只处理 `MouseWheel`）。
  ⚠️ 不能复用 `Viz/VizPanel`：它 `IsHitTestVisible=false` 且只认无输入的 `IVizRenderer`，**收不到滚轮**。
  铺满 bounds 的底槽同时充当"可命中区域"。
- **纯算术** `src/UI/WaveformMath.cs`（离屏可测）：`ZoomAt` / `BucketSpan` / `FollowStart` / `FilePosition` / `ShouldShowLoopMark`。

**播放头的文件位置**（⚠️ 波形的横轴是**文件**，不是播放时间线）：

```
filePos = ProgressPosition < intro ? ProgressPosition : intro + LoopPosition
```

用引擎现成的两个量（`LoopSampleProvider.cs:160/163`），**两种循环模式一条路径、无取模、无特例**；
淡出段 `_srcFrame` 仍在循环体内 ⇒ 标记停在循环段 ✓ 正确。

**缩放后的中位跟随**：

```
view.Start = clamp(filePos − span/2, 0, total − span)
```

✅ **1× 时 `total − span == 0` ⇒ 自动退化为"整轨不滚"** ⇒ 不需要给"没缩放"写特例。

**绘制层次**（自下而上）：底槽 → 中线 → 波形柱 → **循环入口标记** → **播放头**。
⚠️ 标记必须在波形**之上**：满幅波形能占满整个高度，画在下面会被整条盖住 ✗（实机一眼就看出来了）。

## 六、⚠️ 四个踩过的坑（本轮最值钱的部分）

**① 参数收否定 ⇒ 显示条件整个反了**
`SetTrack` 收的实参是 `mayShowMark`（= `!IsTfOneShot`），却被喂进形参 `isTfOneShot` ⇒
**普通曲子不画标记、一次性曲目反而画**，完全反了 ✗。编译器抓不到，肉眼也要试很久。
⇒ **修法：参数收状态本身，不收它的否定。** 这个 bug 是**渲染断言**逮住的。

**② 挑主题色按名字猜 ⇒ 撞色**
标记原本用主题的 `Accent`，看着像"强调色" ⇒ 实际是 `#FF0E639C`（**深蓝**），与波形的
`VizBar #2E86C4`（蓝）撞色、几乎看不见 ✗。
⇒ **挑主题色要查实际色值**；最终新增 `VizMark #FFD4696B`（红），放在可视化那组色里。

**③ 1px 竖线没吸附像素网格 ⇒ "换成红色了却还是灰的"**
线落在两列交界 ⇒ 各 50% 覆盖 + 抗锯齿混色 ⇒ 红 `#D4696B` 与蓝 `#2E86C4` 各半 =
**(129,119,151) 灰紫**，与截图完全吻合。
⇒ 修法：**吸附到设备像素中心**（`(floor(x·dpi)+0.5)/dpi`）+ **笔宽 = 1 设备像素**（不是 1 DIP：
150% 缩放下 1 DIP = 1.5 设备像素，同样糊）。

**④ 播放头挂错节拍 ⇒ 显示不流畅（用户实机反馈）**
挂在既有的 **100ms 轮询**上 ⇒ 每秒只动 10 次 ✗，而可视化走的是 `CompositionTarget.Rendering`
（跟 vsync ≈60Hz）⇒ 并排看就是"一格一跳" ✗。
🔑 **这条教训项目里早就写着** —— `Viz/VizPump.cs:9-11`：「DispatcherTimer 是定时器节拍，和显示器的刷新没有关系」。
我照抄了它的结论，却没照做 ✗。

⇒ 修法两步（**动的东西与不动的分开对待**）：

| | 处理 | 理由 |
| --- | --- | --- |
| 播放头 | 挂 `CompositionTarget.Rendering`（**只在播放中订阅、暂停即退订**）；**不吸附**（亚像素柔边，滑行） | 一直在动 ⇒ 平滑优先 |
| 循环标记 | 保持吸附 | 不动 ⇒ 清晰度优先 |

⚠️ 连带：波形现在**播放中每帧重绘**（几百根柱子，约为可视化 D 面板的 1/10 工作量）⇒
可视化窗口也开着时帧预算紧一点（那块唯一旋钮仍是 D 的余辉层数）。
