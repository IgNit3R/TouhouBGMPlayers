# 决策检查点 —— 切曲滞后的预读方案（已定，未实施）

2026-09-06

## 背景

切曲 / 首次切灵界版的轻微滞后 = build 12 整轨预载的代价（切曲时在 UI 线程同步读
20–50MB 进内存）。用户确认要做预读方案消掉它。

## 已定方案：三个预测源共用一个预读缓存

| 预测源 | 覆盖场景 |
|---|---|
| ① 列表顺序预读 | 自动连播（普通模式播完切下一首） |
| ② 灵界版配对预读 | 首次切灵界版（仅 TH13） |
| ③ 选中即预读（用户提出的思路，优于原"异步加载"） | 手动点歌（含随机模式） |

## 已定约束

- **防抖**：选中停留 ~250ms 才开读，乱扫不触发
- **单槽/双槽缓存**：键 (作品, 曲号)，容量 1–2 条，新预读取消旧的
- **内存上限**：当前播放 + 1~2 条预读 ≈ 100 MB 出头封顶
- 不动的原则：整轨驻留内存的确定性模型（build 12）不变，预读只是把可预测的读取提前
- 预期效果：除"完全无征兆跳从没碰过的曲子"外，所有切换路径零等待

## 状态

**方案确定，暂缓实施** —— 用户要先插入别的任务。开工时以此文件为准。
