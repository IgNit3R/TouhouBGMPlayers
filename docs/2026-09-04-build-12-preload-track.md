# 构建日志 12：整轨驻留内存，根治 loop 折返卡滞

日期：2026-09-04
阶段：第三步 · 用户反馈修复

## 用户反馈（关键）

> 还是有一点卡滞的感觉，但是我发现基本会出现在循环结束点附近。中盘基本没发现卡滞

这句话把范围缩到了一个点：**loop 折返**。

## 根因

循环播放时，播到 `_totalFrames` 要把文件指针 seek 回循环起点。
**那次 seek 之后的第一次读，发生在音频回调内部。**

```
Read(缓冲区)
  ├ 读到音轨末尾
  ├ Seek(循环起点)            ← SetFilePointer，几乎免费
  └ Read(...)                 ← FileStream 缓冲已作废，要真读一次盘（256 KB）
```

而文件是用 `FileOptions.SequentialScan` 打开的 —— 这个标志除了「激进预读」，
还有一半语义是**激进释放读过的页面**（FILE_FLAG_SEQUENTIAL_SCAN 的文档行为）。
对「顺序读到底再跳回开头」这种模式，它正好是反的：
折返时开头早被释放了，于是每次折返都要真读一次盘。

中盘是纯顺序读，有预读兜着，所以没事 —— 与用户描述完全吻合。

## 修法：整轨驻留内存

不再依赖系统缓存的启发式行为，直接把整轨 PCM 读进内存：

- 折返变成一次 `Array.Copy`，**与磁盘快慢完全无关**
- 音频回调里不再有任何磁盘 IO（ seek 和 read 都在内存里 ）
- 文件句柄用完即关，不再长期持有

### 体积实测

| 分位 | 大小 |
|---|---|
| 最小 | 4.3 MB |
| 中位 | 19.9 MB |
| 90% | 31.0 MB |
| 99% | 41.9 MB |
| 最大 | 47.8 MB（TH15 #13 ピュアヒューリーズ） |

全库 7.02 GB，但**同时只有一两首常驻**，峰值约 100 MB。可接受。

### 缓冲区复用池

每首切一次就 new 一个 20–48 MB 的 `byte[]`，会反复触碰大对象堆（LOH），
触发 gen2 回收 —— 那反而会造成新的停顿，等于按下葫芦浮起瓢。

所以加了一个极简的复用池：

```csharp
Rent(size)    // 池里那块够大就直接借出（借出后置空，不能给第二个人）
Return(buf)   // 只保留最大的那块
```

稳态下是「一块在用 + 一块在池里」，切曲不再分配。
交叉淡化期间新旧两个音源同时在，这时会多分配一块，属于正常。

## 性能特征的变化

| | 之前（流式） | 现在（整轨驻留） |
|---|---|---|
| 切曲 | 几乎瞬时 | 一次性读入，约 20–50 ms（热缓存） |
| 中盘 | 每 1.45 秒一次 256 KB 读 | 无 IO |
| **loop 折返** | **一次磁盘读（卡滞来源）** | **一次 memcpy** |
| 常驻内存 | ~256 KB | 4–48 MB / 首 |

切曲那一瞬间的读取发生在 UI 线程，但**音频线程此时仍在播旧链**
（链的替换要等到下一次音频回调），所以听不到空档，只是界面短暂无响应。

## 未改动的部分

- `LoopSampleProvider` 的 `EnsureSourcePosition` 照旧调用 `_source.Seek()` ——
  现在 `Seek` 是纯内存操作，开销为零，但同步逻辑仍需要它
- 旧音源 500 ms 延迟释放的宽限期保留：交叉淡化期间旧链还在读它的缓冲区，
  提前归还给池子会被新音源写脏
- `AudioSourceFactory` 未改动，构造参数不变
