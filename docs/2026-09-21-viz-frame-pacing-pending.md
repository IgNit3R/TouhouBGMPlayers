# 待查：可视化的帧率观感（掉帧感）

日期：2026-09-21
状态：**记录，不做动作**（用户明确「先记录一条不做动作」）

**用户原话**：

> 看上去没啥问题。但是先记录一条不做动作：可视化在某些时候感觉有点帧数不足或者说感觉有点掉帧。

⚠️ 「在某些时候」是关键信息：说明不是持续性的低帧率（那会一眼看出是性能问题），
而是**间歇的顿挫**。所以下面按「什么会让画面停一下」来排，而不是按「什么最费 CPU」。

---

## 候选原因（按可疑度排序，逐条带验证手段）

### 1. 节拍自退订 → 重启的滞后（最像）

`VizPump` 在「不再播放」后约 **1.07 秒**收敛完就**自退订**（M4 的 R2 策略：绝不常驻空转）；
重新起搏靠主窗口那个 **100ms** 的 tick（`RefreshFeedState`）。

于是只要音频出现一次 **> 250ms** 的断续（`VizTap.IsPlaying` 的活动窗口是 250ms）——
设备切换、音频线程被抢占、大 GC —— 判定就会转成「不播」→ 开始淡出 → 退订 ✗
→ 直到下一次 tick 才重新起搏。这几百毫秒里画面是**先淡、再冻、再跳回来**，
被感知成「掉帧」而不是「暂停」正好说得通。

**怎么验**：`VizPump.IdleStoppedCount`（诊断属性已有，但**没有 UI 出口**）；
再加一个「退订 → 重启」的间隔打点。想知道有没有发生，看这个计数涨不涨。

### 2. 拖分隔条时 C+J 的静态层每帧重录

C+J 的静态层（背景 / 底槽 / 刻度线与数字 / 标签）按「面板尺寸 + DPI」缓存（build-43）。
**拖分隔条时尺寸每帧都在变 → 每帧重录那二十来次绘制** —— 这个代价在 build-43 §六 标过，
当时判断「拖动是瞬态、划算」。如果掉帧感出现在拖动那几秒，就是它。

**怎么验**：给静态层的重录次数加个计数（或拖动时看 CPU）。

### 3. 切曲（含切循环模式）时的归零

`PlayTrack` 开头无条件 `NotifyTerminated()` → 画面清零再从零涨起来。
**切循环模式**（同一首重入）也会走这里 —— 那不是"掉帧"，但会被感知成「画面一顿」。
（这条是当时有意选的：清一次比留着上一轮的余辉更正确。）

**怎么验**：不需要验，看现象是否只出现在切曲/改循环模式的瞬间。

### 4. D 的 20 条绘制指令 + 每帧 1 条几何重建

四块合计每帧约 **50KB** 分配 ≈ 3MB/s（build-43 实测）。正常无感，
但**恰好撞上 gen0 回收**时可能抖一帧。

**怎么验**：自检的「每帧分配字节数」已有；要定位抖动得配 `GC.CollectionCount(0)` 打点。

### 5. 分析限频 60Hz 与刷新率的组合

A 的频柱数据来自 **60Hz 的 FFT**（两帧之间复用），而 B/D 取数便宜、**每帧都更新**。
在 144Hz 屏上柱体是「同一份数据画两三遍」，通常不可辨，
但若观者正盯着 A，可能显出与旁边不同的"滞涩感"。

**怎么验**：换 60Hz 屏对比；或临时把 `AnalyzeHz` 提到与刷新率同频看是否消失。
