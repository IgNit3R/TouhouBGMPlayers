# 待查：可视化的帧率观感（掉帧感）

日期：2026-09-21
状态：**记录，不做动作**（用户明确「先记录一条不做动作」）

**用户原话**：

> 看上去没啥问题。但是先记录一条不做动作：可视化在某些时候感觉有点帧数不足或者说感觉有点掉帧。

⚠️ 「在某些时候」是关键信息：说明不是持续性的低帧率（那会一眼看出是性能问题），
而是**间歇的顿挫**。所以下面按「什么会让画面停一下」来排，而不是按「什么最费 CPU」。

---

## 候选原因（按可疑度排序，逐条带验证手段）

### 1. 节拍自退订 → 重启的滞后（最像）

`VizPump` 在「不再播放」后约 **1.07 秒**收敛完就**自退订**（M4 的 R2 策略：绝不常驻空转）；
重新起搏靠主窗口那个 **100ms** 的 tick（`RefreshFeedState`）。

于是只要音频出现一次 **> 250ms** 的断续（`VizTap.IsPlaying` 的活动窗口是 250ms）——
设备切换、音频线程被抢占、大 GC —— 判定就会转成「不播」→ 开始淡出 → 退订 ✗
→ 直到下一次 tick 才重新起搏。这几百毫秒里画面是**先淡、再冻、再跳回来**，
被感知成「掉帧」而不是「暂停」正好说得通。

**怎么验**：`VizPump.IdleStoppedCount`（诊断属性已有，但**没有 UI 出口**）；
再加一个「退订 → 重启」的间隔打点。想知道有没有发生，看这个计数涨不涨。

### 2. 拖分隔条时 C+J 的静态层每帧重录

C+J 的静态层（背景 / 底槽 / 刻度线与数字 / 标签）按「面板尺寸 + DPI」缓存（build-43）。
**拖分隔条时尺寸每帧都在变 → 每帧重录那二十来次绘制** —— 这个代价在 build-43 §六 标过，
当时判断「拖动是瞬态、划算」。如果掉帧感出现在拖动那几秒，就是它。

**怎么验**：给静态层的重录次数加个计数（或拖动时看 CPU）。

### 3. 切曲（含切循环模式）时的归零

`PlayTrack` 开头无条件 `NotifyTerminated()` → 画面清零再从零涨起来。
**切循环模式**（同一首重入）也会走这里 —— 那不是"掉帧"，但会被感知成「画面一顿」。
（这条是当时有意选的：清一次比留着上一轮的余辉更正确。）

**怎么验**：不需要验，看现象是否只出现在切曲/改循环模式的瞬间。

### 4. D 的 20 条绘制指令 + 每帧 1 条几何重建

四块合计每帧约 **50KB** 分配 ≈ 3MB/s（build-43 实测）。正常无感，
但**恰好撞上 gen0 回收**时可能抖一帧。

**怎么验**：自检的「每帧分配字节数」已有；要定位抖动得配 `GC.CollectionCount(0)` 打点。

### 5. 分析限频 60Hz 与刷新率的组合

A 的频柱数据来自 **60Hz 的 FFT**（两帧之间复用），而 B/D 取数便宜、**每帧都更新**。
在 144Hz 屏上柱体是「同一份数据画两三遍」，通常不可辨，
但若观者正盯着 A，可能显出与旁边不同的"滞涩感"。

**怎么验**：换 60Hz 屏对比；或临时把 `AnalyzeHz` 提到与刷新率同频看是否消失。

## ✅ B1 已落地（2026-09-21）：帧统计叠层

`VizPump` 现在记三类数，`VizWindow` 用一个**叠层**显示（默认藏着）：

| 键 | 作用 |
| --- | --- |
| **F12** | 切换统计叠层（**打开时顺手复位峰值**，所以「开一次 → 操作一遍 → 读峰值」就是一次干净测量） |
| **R** | 只复位峰值（中途重来） |

读数是这么一行（贴在可视化窗口右下角）：

```
帧 1234　帧距 均 16.7 峰 33.4ms　分析 均 0.80 峰 6.2ms　绘制 均 1.10 峰 12.4ms　节拍停 3 次
```

### 四个数各判什么

| 数 | 正常值 | 异常说明什么 |
| --- | --- | --- |
| **帧距 均** | 16.7（60Hz）/ 6.9（144Hz） | 均值就偏高 = **持续**跟不上，不是"某些时候" |
| **帧距 峰** | 略高于均值 | ⚠️ **掉帧最直接的证据**：跳到两倍周期就是**实打实丢了一帧**。它涨而 CPU 耗时不高 → 问题在提交/呈现侧（或窗口被别的进程抢） |
| **分析 均/峰** | 均 &lt;1ms | 峰高 = 某帧的 FFT 被卡住（调度、GC） |
| **绘制 均/峰** | 均 ~1ms | 峰高 = 那一帧录了一堆绘制指令（**静态层重录**就是候选 ②） |
| **节拍停 N 次** | **播放期间不该涨** | ⚠️ 涨了 = 音频侧出现过 &gt;250ms 断续 → 候选 ① 成立 |

### 实现上的两个决定

- **峰值可复位**，而不是只给平均：我们追的就是**单帧毛刺**，平均值会把它抹平。
- **帧距用 DWM 给的合成时刻算**（`RenderingEventArgs.RenderingTime`），不用本地时钟 ——
  那才是「这一帧什么时候该上屏」。两条边界（**没有上一帧可比**、**非正间隔**）抽成了纯函数
  `VizPump.CountInterval` 并进了自检：错了不报错、只会让峰值变成垃圾，进而把整次分诊带偏。

- 叠层是**贴角叠层**：不参与尺寸协商，所以开关它**不会动 2.3:1 / 7:3 那套分区比例**。

## 📋 观测协议（= 接入期判据验收，两步并一步）

**为什么能并**：验收要做的动作（拖窗口、切最大化、拉分隔条、跨屏）**恰好就是掉帧最容易出现的场景** ——
一边验一边就把「某些时候」具体化了。

**做法**：打开可视化 → 按 **F12** → 正常做下面这些动作 → 哪个动作之后觉得卡，**记下当时那一行读数**。

| # | 动作 | 该看到什么 |
| --- | --- | --- |
| 1 | 窗口化，拖可视化窗口的**上 / 下 / 左**边缘 | **完全没反应**（贴附下只允许拖右边缘） |
| 2 | 拖**右边缘** | 只改宽度，**高度纹丝不动**；关掉再开/重启后宽度被记住 |
| 3 | 切**最大化** | 附件窗口消失、画面进主窗口右侧一列、曲目表被挤窄 |
| 4 | 拖**分隔条** | 能调宽窄；松手后宽度落盘（`EmbeddedWidth`） |
| 5 | 还原窗口 | 内嵌列收回、附件窗口回来，**画面接着动**（不该从零重来） |
| 6 | **最小化**主窗口 | 两个都不显示 |
| 7 | 把主窗口拖到**屏幕最右** | 可视化窗口仍然**完整可见**（不该跑出屏幕） |
| 8 | **跨屏**（若有两块屏） | 来回拖几次，位置**不累计漂移** |
| 9 | 关主窗口 | 可视化窗口一起消失，进程干净退出 |
| 10 | 关掉可视化开关 | 主窗口**逐像素**与没有这个功能时一致 |

**⚠️ 第 1 条是重点**：它对应的机制（`WM_SIZING` 钩子）**在隔离期一直是惰性的**
（`Attached` 恒 false），**接入之后才第一次真的生效** —— 也就是到现在**从没在实机跑过**。

**回报时给这两个**：① 哪个动作之后觉得卡 ② 那一行读数（或截个图）。有这两样就能直接分诊，
不必再猜。

## ✅ 结案（2026-09-21 03:48）：D 是元凶，而且**成本正比于层数**

### 决定性对照

| | 帧距 均 |
| --- | --- |
| D 开（20 层） | **25.0 ~ 27.6ms** |
| D 关 | **5.1ms** |

⇒ D 一开就吃掉约 **20ms/帧**。

### 第一个假设（每段成本）**被测量推翻**

先按「段数太多」动手：投影时抽稀（`PointStride = 2`，**段数 8000 → ~4000**）。结果：

| | 段数 | 帧距 均 |
| --- | --- | --- |
| 改前 | 8000 | 27.6ms |
| 改后 | **~4000（-50%）** | **25.0ms（-9%）** |

**段数砍半只降 9%** ⇒ 不是每段的账 ✗。

### 真正的账：**墨量 = 层数 × 每层的线长 × 线宽**

- 成本 **正比于层数**：20 层 ≈ 20ms ⇒ **约 1ms/层**；
- 每层的**线长**由信号决定：Lissajous 的点散得越开，路径在团里窜得越长
  ⇒ **响的时候墨量更大** ⇒ **这就是「音乐越响越掉帧」的由来** ✓
- 抽稀只是把折线取直一点，**路径长度几乎没变**，所以没用 ✓ 完全自洽。

### 已落地的两件事

1. **`PointStride = 2`**（抽稀）：**没解决症状**，但它把每帧分配从 22.4KB 降到 11.2KB，无害，留着。
2. **余辉层数做成可调**：`VizSettings.TrailLayers`（4～20，**默认 20 = 观感逐位不变**）
   + 设置页「性能 → D 余辉层数」。
   淡出系数**按层数重新标定**（指数 `20/n`），所以调小后**最老那层的亮度落在同一档** ——
   观感是「雾薄了、渐变粗了」，而不是「外面多出一圈硬边」。

### 层数 → 帧距的估算（线性外推，**用户可自行实测校准**）

| 层数 | 估算帧距 | 折算 |
| --- | --- | --- |
| 20（默认） | ~25ms | ~40fps |
| 14 | ~19ms | ~53fps |
| 10 | ~15ms | ~67fps |
| 6 | ~11ms | ~90fps |
| 4（下限） | ~9ms | ~110fps |

⚠️ **别指望 D 免费**：它的观感就是"叠多少条线"，墨量省不掉。
参照页之所以便宜，是因为它**每帧只画 1 条折线**、余辉靠**持久画布**累积（= 1/20 的墨量）——
但那条路要 `RenderTargetBitmap`（同步 + 回读，每帧 5ms 起），**M2 当时否掉是对的**：
换过去很可能比现在还慢。所以这里不做大改，只给旋钮。

### 顺带一条方法论

> 这次是「**假设 → 改 → 量 → 假设被推翻 → 重新定位**」的完整一轮。
> 抽稀那一刀如果只凭推断就收工，症状会被记成"已修"，而它根本没修掉 ——
> **仪器（F12 那行数）的价值就在这里**。

用户按 5 / 10 / 15 / 20 四档各量了一次（同一首曲子，响度略有差异 → ±10% 噪声）：

| 层数 | 帧距 均 | 折算 | 帧距 峰 |
| --- | --- | --- | --- |
| 0（D 关） | **5.1ms** | ~196fps | 33.5ms |
| 5 | **9.4ms** | ~106fps | 29.3ms |
| 10 | **16.3ms** | ~61fps | 25.0ms |
| 15 | **21.6ms** | ~46fps | 29.2ms |
| 20（默认） | **26.7ms** | ~37fps | 37.5ms |

**模型：`帧距 ≈ 5.1 + 1.05 × 层数`（毫秒）** —— 线性，每层约 **1.05ms**。

- 5.1ms 正好是这块 200Hz 屏的一个刷新周期 ⇒ **基线是被 vsync 卡住的，已经满帧** ✓
- 「每层 1.05ms」这个价码**与段数无关**（段数减半时每层成本没变）⇒
  结合「越响越慢」，坐实了是**填充率**：每层铺下的**墨量 = 路径长度 × 线宽**，
  而路径长度随幅度增长。

### 已排除的免费手段

- 几何与画笔**都已 `Freeze()`** ✓（不是这个）
- Viz 代码里**没有** `GuidelineSet` / `EdgeMode` / `RenderOptions`（那些会让整幅绘制掉回软件）✓
- `渲染 2` = 进程级完全硬件加速 ✓

⇒ 剩下这 1.05ms/层 只能出在 **MIL 的光栅化侧**（CPU 或弱 GPU 混合），**不在我们的代码里**。
所以**不再往这个方向深挖**：旋钮已经能覆盖需求，而换架构（持久画布）要付 `RenderTargetBitmap`
的同步 + 回读（每帧 5ms 起）—— 很可能比现在还慢。

### 选型建议

| 取舍 | 层数 | 观感 | 帧率 |
| --- | --- | --- | --- |
| 观感优先 | 20 | 密实的雾（方案原定） | ~37fps |
| **折中** | **10** | 仍是明显的团雾，略薄 | **~61fps** |
| 流畅优先 | 5 | 明显的稀疏笔画 | ~106fps |

⚠️ **帧距 峰（25~37ms）不随层数下降** —— 那是另一条账（偶发一帧被卡住，量级与 D 无关），
大概来自 GC 或外部调度，**本档不追**。

### 仍未处理

- **默认值**：**已定（2026-09-21 用户拍板）：默认改成 10**（`VizSettings.DefaultTrailLayers`）。
  理由：新装的机器不该一打开就是 37fps；10 层仍是明显的团雾、帧率 ~61fps。
  方案原定的密实（20）仍可调回去。用户自己的安装实测选了 **7 层**（≈12.5ms ≈ 80fps）。
